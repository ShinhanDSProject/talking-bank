# 04. 공통 도메인 규칙

> 모든 도메인이 따르는 용어와 규칙. 각 도메인의 엔티티 상세는 [`domains/`](domains/) 아래 도메인 문서에 있다.

## 용어

| 용어          | 정의                                                                     | 코드           | 도메인  |
| ------------- | ------------------------------------------------------------------------ | -------------- | ------- |
| 회원          | 가입해서 로그인하는 사람. 계좌를 여러 개 가질 수 있다                    | `User`         | 코어    |
| 계좌          | 돈이 들어 있는 단위. 계좌번호로 식별. 회원 한 명에 속한다                | `Account`      | 코어    |
| 잔액          | 계좌에 지금 있는 돈. 음수가 될 수 없다                                   | `balance`      | 코어    |
| 거래          | 계좌 하나의 잔액이 바뀐 기록. 입금 아니면 출금. **한 번 쓰면 안 바꾼다** | `Transaction`  | 코어    |
| 이체(송금)    | 한 계좌에서 다른 계좌로 돈을 옮기는 요청. 성공하면 거래 2건이 생긴다     | `Transfer`     | 코어    |
| 이상거래 판정 | FDS 규칙이 출금 요청을 평가한 결과                                       | `FdsAlert`     | Phase 2 |
| 자동이체      | 정해진 날에 반복 실행되는 이체 예약                                      | `AutoTransfer` | Phase 3 |

"거래"와 "이체"를 섞어 쓰지 않는다. **이체는 요청이고, 거래는 결과다.**

## 금액 규칙

1. **`BigDecimal`만 쓴다. `double`·`float` 금지.** `0.1 + 0.2 != 0.3`이다.
2. **KRW는 정수다.** 소수점 이하가 생기면 버그다. DB 컬럼은 `DECIMAL(19,2)`로 두되 로직에서는 `setScale(0)`을 검증한다.
3. **`BigDecimal` 비교는 `compareTo`로 한다.** `equals`는 `1.00`과 `1`을 다르다고 본다.
4. **잔액은 음수가 될 수 없다.** DB 제약(`CHECK balance >= 0`)과 코드 검증을 둘 다 둔다.
5. **잔액은 컬럼에 저장한다.** 매번 거래내역을 합산하지 않는다. 대신 `Transaction.balanceAfter`로 정합성을 검증하는 테스트를 둔다.

## 송금 규칙

송금은 하나의 `@Transactional` 안에서 아래 순서로 처리한다.

```
1. 멱등성 확인   idempotencyKey가 이미 있으면 그 결과를 그대로 반환
2. 검증          출금≠입금 계좌, 금액>0, 두 계좌 모두 ACTIVE
3. 잠금          두 계좌를 ID 오름차순으로 비관적 락 (SELECT ... FOR UPDATE)
4. 잔액 확인     출금 계좌 잔액 ≥ 금액. 아니면 FAILED
5. 출금 평가 훅  Phase 1은 항상 통과. Phase 2에서 FDS가 구현체로 들어와 HOLD → PENDING_AUTH / BLOCK → BLOCKED
6. 출금          fromAccount.balance -= amount, Transaction(WITHDRAWAL) 생성
7. 입금          toAccount.balance += amount, Transaction(DEPOSIT) 생성
8. 완료          Transfer.status = COMPLETED
```

6~8 중 어디서든 예외가 나면 전부 롤백된다. **"출금은 됐는데 입금이 안 된" 상태는 존재할 수 없다.** 이걸 테스트로 증명한다.

### 동시성

- **비관적 락**(`@Lock(PESSIMISTIC_WRITE)`)을 쓴다. 낙관적 락 + 재시도보다 단순하고, 은행처럼 충돌이 실제로 일어나는 곳에 맞다.
- **데드락 방지**: A→B 이체와 B→A 이체가 동시에 오면 서로 상대 락을 기다린다. 항상 **계좌 ID 오름차순**으로 잠근다.
- 검증: 스레드 N개가 같은 계좌에서 동시에 출금하는 테스트. 최종 잔액 = 초기 잔액 − 성공 건수 × 금액.

### 멱등성

- 클라이언트가 이체 화면 진입 시 UUID를 만들어 `idempotencyKey`로 보낸다.
- 서버는 같은 키가 이미 있으면 새로 처리하지 않고 기존 `Transfer` 결과를 돌려준다.
- `idempotencyKey`는 unique 제약이라 동시에 같은 키가 와도 하나만 INSERT된다.

## 거래 불변 규칙

`Transaction`은 UPDATE·DELETE 하지 않는다. 잘못된 거래는 반대 거래를 추가해서 바로잡는다.

## 이후 Phase를 위해 코어가 열어둘 자리

| 코어 모델     | 열어둘 자리                                                                                                                                                                        | 어느 Phase가 쓰나 |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `Account`     | `accountType` 컬럼 — 지금은 `CHECKING`(입출금) 하나. 뒤에 `DEPOSIT`, `LOAN`, `SECURITIES` 추가                                                                                     | Phase 3, 6        |
| `Transaction` | `sourceType` 컬럼 — 이 거래가 어디서 왔는지. `TRANSFER`, `CARD`, `SECURITIES`, `INSURANCE`, `INTEREST`                                                                             | Phase 3, 5, 6, 7  |
| `Transfer`    | 이체 로직을 **서비스 메서드 하나**(`TransferService.execute`)로 노출. 카드 출금·예수금 이체·보험료 납입이 이걸 호출                                                                | Phase 5, 6, 7     |
| 출금 평가 훅  | **출금 평가 훅** — `TransferService`가 출금 전에 호출하는 인터페이스. Phase 1 구현체는 항상 통과. 평가 대상이 "이체"가 아니라 "출금 요청"이라 카드·증권·보험 출금도 같은 훅을 탄다 | Phase 2           |
| `User`        | 생년월일 컬럼 자리 — 대출 심사·보험 청약에서 필요                                                                                                                                  | Phase 3, 7        |

`accountType`과 `sourceType`은 Phase 1에서 값이 하나뿐이라도 **컬럼은 지금 만든다.**

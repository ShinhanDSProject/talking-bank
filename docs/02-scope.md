# 02. 범위와 기능 명세

> 범위를 바꿀 때는 이 문서를 먼저 고친다.

## 범위 원칙

1. **은행 코어(Phase 1)를 먼저, 깊게 만든다.**
2. **Phase는 순서대로 진행한다.** 앞 Phase의 완료 조건을 만족하기 전에 다음 Phase를 시작하지 않는다. 완료 조건은 [05-schedule.md](05-schedule.md)에 있다.
3. **Phase 안에서는 P0 → P1 → P2 순서로만 진행한다.** P0가 끝나기 전에 P1을 시작하지 않는다.
4. **각 확장 도메인은 코어와 연결되는 핵심 흐름 하나만 구현한다.** 카드라면 "승인 → 계좌 출금 → 정산" 한 줄이지, 카드사 전체가 아니다.
5. **제외 항목은 이유와 함께 이 문서에 남긴다.**
6. **AI는 판단하지 않고 설명만 한다.** 돈을 움직이는 결정은 코드(룰·트랜잭션)가 하고, LLM은 그 결과를 사람이 읽기 쉽게 풀어주는 데만 쓴다. (AI 기능 자체는 아직 미정)

## Phase 개요

| Phase | 도메인              | 코어와의 연결점                      | 핵심 흐름                                                       | 배치                       |
| ----- | ------------------- | ------------------------------------ | --------------------------------------------------------------- | -------------------------- |
| **1** | **은행 코어 + FDS** | —                                    | 가입 → 계좌 → 송금 → 거래내역 → 이상거래 탐지 → 관리자          | 없음                       |
| 2     | 여신/수신 상품      | 예금·대출 계좌가 입출금 계좌에 연결  | 적금 가입 → 자동이체 납입 → 만기 해지 / 대출 실행 → 원리금 상환 | 자동이체, 이자 계산, 연체  |
| 3     | 오픈뱅킹            | 우리 계좌를 외부 앱에 노출           | 외부 앱 등록 → OAuth 동의 → 계좌 조회·이체 API 호출             | 동의 만료 관리             |
| 4     | 카드                | 체크카드가 입출금 계좌에서 즉시 출금 | 결제 승인 → 계좌 출금 → 매입 → 가맹점 정산                      | 일마감 매입, 정산 지급     |
| 5     | 증권                | 증권 계좌 입금이 은행 계좌에서 출금  | 예수금 입금 → 가상 매수/매도 → 체결 → T+2 결제                  | T+2 결제, 일일 평가        |
| 6     | 보험                | 보험료가 은행 계좌에서 자동이체      | 청약 → 승인 → 보험료 납입 → 만기 환급 / 실효                    | 보험료 자동이체, 만기 도래 |

Phase 2부터 Spring Batch가 들어온다. Phase 2~6의 순서는 바꿔도 된다 — 단, **하나씩** 한다.

## Phase 2 이후 — 확장 도메인

각 Phase의 상세 기능 명세는 **그 Phase에 착수할 때** 쓴다. 지금은 코어와의 연결점과 새로 생기는 모델 후보만 적는다. 코어 설계가 이 연결점을 막지 않도록 하기 위해서다.

### Phase 2 — 여신/수신 상품

- **수신(예금)**: 적금 상품 가입 → 매월 은행 계좌에서 자동이체로 납입 → 만기 시 원금 + 이자를 은행 계좌로 지급.
- **여신(대출)**: 대출 신청 → 승인 → 대출금을 은행 계좌로 입금 → 원리금 상환 스케줄 생성 → 매월 자동이체로 상환. 연체 시 등급 변경.
- 새 모델 후보: `Product`(상품 마스터), `DepositAccount`, `LoanAccount`, `RepaymentSchedule`, `AutoTransfer`.
- 이자 계산은 단리/복리 공식을 `BigDecimal`로.

### Phase 3 — 오픈뱅킹

- 우리 은행이 **제공자**다. 외부 앱(가상)이 OAuth 2.0으로 사용자 동의를 받고 계좌 조회·이체 API를 호출한다.
- Access Token / Refresh Token, 스코프(`account:read`, `transfer:write`), 동의 이력, 동의 만료 알림.
- 기존 AUTH의 JWT와 별개의 인가 서버 역할이 필요하다. Spring Authorization Server 검토.
- 새 모델 후보: `OAuthClient`, `UserConsent`, `OAuthToken`.

### Phase 4 — 카드

- 체크카드만. 신용카드(청구 사이클)는 하지 않는다.
- 결제 승인 요청 → 은행 계좌 잔액 확인 → 즉시 출금(코어의 송금 로직 재사용) → 승인 응답. 이후 매입 → 가맹점별 정산 배치.
- 새 모델 후보: `Card`, `Merchant`, `CardApproval`, `Settlement`.

### Phase 5 — 증권

- 증권 계좌 개설 → 은행 계좌에서 예수금 이체 → 가상 종목 매수/매도 → 즉시 체결(가상) → T+2 결제 배치 → 일일 포트폴리오 평가.
- 실제 시세는 연동하지 않는다. 종목 몇 개와 시세를 시드로 둔다.
- 영업일/공휴일 캘린더 테이블이 필요하다 — Phase 2의 배치에서 미리 만들어두면 재사용.
- 새 모델 후보: `SecuritiesAccount`, `Stock`, `Order`, `Execution`, `Holding`, `BusinessDay`.

### Phase 6 — 보험

- 청약 → 규칙 기반 자동 심사(언더라이팅) → 계약 → 매월 보험료 자동이체 → 만기 환급 / 미납 시 실효 / 부활.
- 계약 상태 머신(청약 → 유효 → 실효 → 부활 / 만기 / 해지)이 핵심이다.
- 새 모델 후보: `InsuranceProduct`, `Policy`, `PremiumPayment`, `Claim`.

## 범위에서 제외 — 이 프로젝트에서는 하지 않는다

| 항목                                                            | 제외 이유                                                                                                                              |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| ML/DL 모델 학습 기반 FDS                                        | 레이블된 실거래 데이터가 없어 학습·평가가 불가능하다. 룰 기반으로 구현한다.                                                            |
| 실제 외부 금융망 연동 (타행 이체, 실시간 시세, 실제 오픈뱅킹망) | 인증·계약이 필요하다. 타행 계좌는 우리 DB 안의 다른 사용자 계좌로, 시세는 시드 데이터로, 오픈뱅킹은 "우리가 제공하는 쪽"으로 대체한다. |
| 신용카드 청구 사이클                                            | Phase 4는 체크카드까지. 이용일 → 매입 → 청구 마감 → 결제일의 월 단위 흐름은 범위 밖.                                                   |
| 다중 통화                                                       | KRW만 지원한다. `currency` 컬럼은 남겨두되 로직에서는 KRW로 고정한다.                                                                  |
| 프로덕션급 인프라 (k8s, CI/CD 파이프라인, 모니터링 스택)        | 배포는 Docker Compose + 서버 한 대로 한다.                                                                                             |
| 시스템 상태 대시보드 직접 제작                                  | actuator 엔드포인트 노출 정도로 갈음한다.                                                                                              |
| 소셜 로그인, 이메일 인증 메일                                   | 아래 "미확정 스코프"에 따라 결정. 기본은 제외.                                                                                         |

## Phase 1 기능 명세

각 기능의 **수용 조건(AC)** 을 적는다. 상세 API 설계는 구현 담당자가 이슈에서 한다.

### AUTH — 회원가입 · 로그인

세부 태스크는 이슈 #14 ~ #26(`AUTH-00` ~ `AUTH-12`)에 이미 나뉘어 있다.

- 이메일·비밀번호·휴대폰 번호로 가입한다. 이메일·휴대폰 중복을 확인한다.
- 로그인 성공 시 Access Token + Refresh Token을 발급한다. 정책은 [06-conventions.md](06-conventions.md#인증-정책) 참고.
- 인증이 필요한 API는 토큰 없이 호출하면 401을 돌려준다.
- 로그아웃하면 Refresh Token이 무효화된다.

**AC**

- [ ] 중복 이메일로 가입 시 명확한 에러 코드가 온다.
- [ ] 만료된 Access Token으로 호출 시 401, Refresh로 재발급이 된다.
- [ ] 로그아웃 후 Refresh Token으로 재발급이 안 된다.

### ACCT — 계좌 조회

- 가입 시 기본 입출금 계좌가 하나 자동 개설된다. (계좌 개설 화면은 만들지 않는다.)
- 내 계좌 목록과 각 잔액을 본다. 다른 사람의 계좌는 볼 수 없다.

**AC**

- [ ] 다른 사용자의 계좌 ID로 조회하면 403 또는 404가 온다.
- [ ] 잔액은 거래내역의 합과 항상 일치한다. (테스트로 검증)

### XFER — 송금

규칙은 [04-domain.md](04-domain.md#송금-규칙) 에 정리한다. **Phase 4(카드 출금), Phase 5(예수금 이체), Phase 6(보험료 납입)이 전부 이 로직을 재사용한다.**

- 출금 계좌(내 계좌) · 입금 계좌번호 · 금액 · 메모를 입력한다.
- 확인 화면에서 수취인 이름을 보여준 뒤 실행한다.
- 실행 결과(성공 / 잔액 부족 / FDS 차단 / FDS 보류)를 화면에 보여준다.

**AC**

- [ ] 잔액보다 큰 금액은 거절되고 잔액이 변하지 않는다.
- [ ] 출금 계좌와 입금 계좌가 같으면 거절된다.
- [ ] 동일 계좌에 동시 출금 N건을 보내도 최종 잔액이 음수가 되지 않는다. (동시성 테스트)
- [ ] 입금 처리 중 예외가 나면 출금도 롤백된다. (트랜잭션 테스트)
- [ ] 같은 요청을 두 번 보내도(더블 클릭) 한 번만 이체된다. (멱등성)

### TXN — 거래내역

- 계좌별 입금/출금 내역을 최신순으로 본다. 기간 필터를 지원한다.
- 각 거래에는 거래번호, 유형(입금/출금), 금액, 거래 후 잔액, 상대 계좌, 시각, 메모가 있다.

**AC**

- [ ] 송금 1건이 출금 계좌 내역과 입금 계좌 내역 양쪽에 각각 1건씩 남는다.
- [ ] 목록은 페이지네이션된다. (기본 20건)

### FDS — 룰 기반 이상거래 탐지

**실시간 룰**만 구현한다. 야간 배치는 Phase 2에서 배치 인프라가 들어온 뒤에 한다.

초기 규칙(안). 임계값은 설정으로 뺀다.

| 규칙             | 조건                         | 결과 |
| ---------------- | ---------------------------- | ---- |
| 고액 이체        | 1회 금액 ≥ N원               | 보류 |
| 단시간 반복      | 최근 M분 내 이체 K건 이상    | 보류 |
| 신규 수취인 고액 | 처음 보내는 계좌에 N'원 이상 | 보류 |
| 한도 초과        | 1일 누적 이체 ≥ 일한도       | 차단 |

- **보류**: 이체를 실행하지 않고 사용자에게 추가 인증(예: 비밀번호 재입력)을 요구한다. 통과 시 실행.
- **차단**: 이체를 거절하고 관리자 목록에 남긴다.
- 모든 판정은 `fds_alert`(가칭)에 기록한다 — 규칙, 점수, 결과, 시각.
- Phase 4 이후 카드·증권·보험의 출금도 같은 FDS를 거친다. 규칙 인터페이스가 "이체"에만 묶이지 않게 설계한다.

**AC**

- [ ] 각 규칙에 대해 걸리는 케이스와 안 걸리는 케이스 테스트가 있다.
- [ ] 보류된 이체는 추가 인증 통과 전까지 잔액이 변하지 않는다.
- [ ] FDS 평가 자체가 실패(예외)해도 송금이 임의로 실행되지 않는다. (fail-closed)

### ADMIN — 관리자 조회

- 관리자 권한(`ROLE_ADMIN`)을 가진 계정만 접근한다.
- 이상거래 목록: 시각, 회원, 금액, 걸린 규칙, 결과. 상세 보기.
- 거래 로그: 전체 거래를 최신순으로. 검색은 계좌번호·기간 정도.

**AC**

- [ ] 일반 사용자 토큰으로 관리자 API 호출 시 403.

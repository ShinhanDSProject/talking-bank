# 02. 범위와 기능 명세

> 4주 프로젝트에서 가장 중요한 문서다. "이것도 하자"는 말이 나올 때마다 여기로 돌아온다.

## 범위 원칙

1. **은행 전체가 아니라 "계좌와 송금"을 제대로 만든다.** 15개 기능이 절반씩 되다 만 것보다, 송금 하나가 동시성까지 정확히 동작하는 쪽이 압도적으로 낫다.
2. **우선순위는 P0 → P1 → P2 순서로만 진행한다.** P0가 끝나기 전에 P1을 시작하지 않는다.
3. **제외 항목은 "향후 계획"으로 발표한다.** 안 만든 것을 숨기지 않고, 왜 뺐는지 설명한다.
4. **AI는 판단하지 않고 설명만 한다.** 돈을 움직이는 결정은 코드(룰·트랜잭션)가 하고, LLM은 그 결과를 사람이 읽기 쉽게 풀어주는 데만 쓴다. (AI 기능 자체는 아직 미정 — 아래 P2 참고)

## 우선순위별 기능

### P0 — 없으면 프로젝트가 실패한 것

| ID   | 기능              | 요약                                                       |
| ---- | ----------------- | ---------------------------------------------------------- |
| AUTH | 회원가입 · 로그인 | 이메일/비밀번호 가입, JWT 로그인, 토큰 재발급, 로그아웃    |
| ACCT | 계좌 조회         | 내 계좌 목록, 계좌별 잔액, 계좌 상세                       |
| XFER | 송금              | 내 계좌 → 다른 계좌 이체. 잔액 검증, 트랜잭션, 동시성 제어 |
| TXN  | 거래내역          | 계좌별 입출금 내역, 최신순, 기간 필터, 상세                |

### P1 — 있어야 "완성"이라 부를 수 있는 것

| ID    | 기능                  | 요약                                                           |
| ----- | --------------------- | -------------------------------------------------------------- |
| FDS   | 룰 기반 이상거래 탐지 | 송금 요청 시 규칙 3~4개로 평가 → 정상 / 보류(추가 인증) / 차단 |
| ADMIN | 관리자 조회 화면      | 이상거래 목록, 전체 거래 로그 — **읽기 전용**                  |
| CMN   | 공통 기반             | 에러 응답 표준화, 공통 예외 처리, Swagger API 문서             |

### P2 — 시간이 남으면, 아니면 "향후 계획"

| ID    | 기능               | 비고                                                             |
| ----- | ------------------ | ---------------------------------------------------------------- |
| AUTO  | 자동이체           | 등록·삭제·조회 + Spring Batch로 실행일에 이체. 배치 학습 목적    |
| AI    | AI 기능 (미정)     | 후보: FDS 탐지 결과 설명 생성, 소비 리포트, 거래내역 자연어 검색 |
| ADMIN | 관리자 — 회원 관리 | 회원 목록·검색·상세                                              |
| MON   | 시스템 상태        | actuator 노출 정도. 대시보드 직접 제작은 안 함                   |

### 범위에서 제외 — 이번 프로젝트에서는 하지 않는다

| 항목                                                     | 제외 이유                                                                                                                                                                                   |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ML/DL 모델 학습 기반 FDS                                 | 레이블된 실거래 데이터가 없다. 합성 데이터로 학습한 모델은 의미가 없고, 4주 안에 학습·서빙·평가가 불가능하다. 룰 기반으로 정확히 만들고 "어떤 조건이면 ML이 필요한지"를 설명하는 쪽이 낫다. |
| 실제 오픈뱅킹·외부 금융망 연동                           | 인증·계약이 필요하다. 타행 계좌는 우리 DB 안의 다른 사용자 계좌로 대체한다.                                                                                                                 |
| 대출·예적금·카드 등 상품                                 | 주제를 "계좌와 송금"으로 좁힌다.                                                                                                                                                            |
| 다중 통화                                                | KRW만 지원한다. `currency` 컬럼은 남겨두되 로직에서는 KRW로 고정한다.                                                                                                                       |
| 프로덕션급 인프라 (k8s, CI/CD 파이프라인, 모니터링 스택) | 4주 프로젝트의 배포는 Docker Compose + 서버 한 대로 충분하다. 인프라에 2주를 쓰고 핵심 기능이 미완성인 채 발표하는 것이 초심자 팀의 가장 흔한 실패다.                                       |
| 시스템 상태 대시보드 직접 제작                           | actuator 엔드포인트 노출 정도로 갈음한다.                                                                                                                                                   |
| 소셜 로그인, 이메일 인증 메일                            | 아래 "미확정 스코프"에 따라 결정. 기본은 제외.                                                                                                                                              |

## 기능 명세

각 기능의 **수용 조건(AC)** 을 적는다. 상세 API 설계는 구현 담당자가 이슈에서 한다.

### AUTH — 회원가입 · 로그인

세부 태스크는 이슈 #14 ~ #26(`AUTH-00` ~ `AUTH-12`)에 이미 나뉘어 있다.

- 이메일·비밀번호·휴대폰 번호로 가입한다. 이메일·휴대폰 중복을 확인한다.
- 로그인 성공 시 Access Token + Refresh Token을 발급한다. 정책은 [06-conventions.md](06-conventions.md#인증-정책) 참고.
- 인증이 필요한 API는 토큰 없이 호출하면 401을 돌려준다.
- 로그아웃하면 Refresh Token이 무효화된다.

**AC**

- [ ] 중복 이메일로 가입 시 명확한 에러 코드가 온다.
- [ ] 만료된 Access Token으로 호출 시 401, Refresh로 재발급이 된다.
- [ ] 로그아웃 후 Refresh Token으로 재발급이 안 된다.

### ACCT — 계좌 조회

- 가입 시 기본 입출금 계좌가 하나 자동 개설된다. (계좌 개설 화면은 만들지 않는다.)
- 내 계좌 목록과 각 잔액을 본다. 다른 사람의 계좌는 볼 수 없다.

**AC**

- [ ] 다른 사용자의 계좌 ID로 조회하면 403 또는 404가 온다.
- [ ] 잔액은 거래내역의 합과 항상 일치한다. (테스트로 검증)

### XFER — 송금

이 프로젝트의 심장이다. 규칙은 [04-domain.md](04-domain.md#송금-규칙) 에 정리한다.

- 출금 계좌(내 계좌) · 입금 계좌번호 · 금액 · 메모를 입력한다.
- 확인 화면에서 수취인 이름을 보여준 뒤 실행한다.
- 실행 결과(성공 / 잔액 부족 / FDS 차단 / FDS 보류)를 화면에 보여준다.

**AC**

- [ ] 잔액보다 큰 금액은 거절되고 잔액이 변하지 않는다.
- [ ] 출금 계좌와 입금 계좌가 같으면 거절된다.
- [ ] 동일 계좌에 동시 출금 N건을 보내도 최종 잔액이 음수가 되지 않는다. (동시성 테스트)
- [ ] 입금 처리 중 예외가 나면 출금도 롤백된다. (트랜잭션 테스트)
- [ ] 같은 요청을 두 번 보내도(더블 클릭) 한 번만 이체된다. (멱등성)

### TXN — 거래내역

- 계좌별 입금/출금 내역을 최신순으로 본다. 기간 필터를 지원한다.
- 각 거래에는 거래번호, 유형(입금/출금), 금액, 거래 후 잔액, 상대 계좌, 시각, 메모가 있다.

**AC**

- [ ] 송금 1건이 출금 계좌 내역과 입금 계좌 내역 양쪽에 각각 1건씩 남는다.
- [ ] 목록은 페이지네이션된다. (기본 20건)

### FDS — 룰 기반 이상거래 탐지

스터디 자료 4팀의 "실시간 룰 + 야간 배치" 구조 중 **실시간 룰**을 구현한다. 야간 배치는 P2 AUTO와 묶어 시간이 남으면 한다.

초기 규칙(안). 임계값은 설정으로 뺀다.

| 규칙             | 조건                         | 결과 |
| ---------------- | ---------------------------- | ---- |
| 고액 이체        | 1회 금액 ≥ N원               | 보류 |
| 단시간 반복      | 최근 M분 내 이체 K건 이상    | 보류 |
| 신규 수취인 고액 | 처음 보내는 계좌에 N'원 이상 | 보류 |
| 한도 초과        | 1일 누적 이체 ≥ 일한도       | 차단 |

- **보류**: 이체를 실행하지 않고 사용자에게 추가 인증(예: 비밀번호 재입력)을 요구한다. 통과 시 실행.
- **차단**: 이체를 거절하고 관리자 목록에 남긴다.
- 모든 판정은 `fds_alert`(가칭)에 기록한다 — 규칙, 점수, 결과, 시각.

**AC**

- [ ] 각 규칙에 대해 걸리는 케이스와 안 걸리는 케이스 테스트가 있다.
- [ ] 보류된 이체는 추가 인증 통과 전까지 잔액이 변하지 않는다.
- [ ] FDS 평가 자체가 실패(예외)해도 송금이 임의로 실행되지 않는다. (fail-closed)

### ADMIN — 관리자 조회

- 관리자 권한(`ROLE_ADMIN`)을 가진 계정만 접근한다.
- 이상거래 목록: 시각, 회원, 금액, 걸린 규칙, 결과. 상세 보기.
- 거래 로그: 전체 거래를 최신순으로. 검색은 계좌번호·기간 정도.

**AC**

- [ ] 일반 사용자 토큰으로 관리자 API 호출 시 403.

## 미확정 스코프 — 지금 결정해야 하는 것

이슈 #14(`AUTH-00`)에서 제기된 항목이다. **DB 설계(AUTH-02) 전에 답이 나와야 한다.** 나중에 추가하면 마이그레이션 + API + 화면을 전부 고쳐야 한다.

| #   | 항목                           | 이 문서의 제안                                                 | 결정 |
| --- | ------------------------------ | -------------------------------------------------------------- | ---- |
| 1   | 회원가입 시 수집 개인정보 범위 | 이메일·비밀번호·이름·휴대폰. 생년월일은 컬럼만 확보            | ⬜   |
| 2   | 약관 동의 처리                 | 1차 제외. 동의 이력 테이블 자리만 확보                         | ⬜   |
| 3   | 이메일 인증 메일               | 제외. 메일 인프라가 필요해 스코프가 크게 늘어남                | ⬜   |
| 4   | 소셜 로그인                    | 제외                                                           | ⬜   |
| 5   | 관리자 계정·권한 구분          | **필요**. ADMIN 기능이 P1이므로 `role` 컬럼과 JWT claim에 포함 | ⬜   |

결정되면 ⬜를 ✅로 바꾸고 결정 내용을 적는다.

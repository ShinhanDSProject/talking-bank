# 02. 범위

> 범위를 바꿀 때는 이 문서를 먼저 고친다. 각 Phase의 기능 명세·모델·진행 순서는 [`domains/`](domains/) 아래 도메인 문서에 있다.

## 범위 원칙

1. **은행 코어(Phase 1)를 먼저, 깊게 만든다.**
2. **Phase는 순서대로 진행한다.** 앞 Phase의 완료 조건을 만족하기 전에 다음 Phase를 시작하지 않는다. 완료 조건은 각 도메인 문서에 있다.
3. **Phase 안에서는 P0 → P1 → P2 순서로만 진행한다.** P0가 끝나기 전에 P1을 시작하지 않는다.
4. **각 확장 도메인은 코어와 연결되는 핵심 흐름 하나만 구현한다.** 카드라면 "승인 → 계좌 출금 → 정산" 한 줄이지, 카드사 전체가 아니다.
5. **지금 하지 않는 것은 다시 볼 조건과 함께 향후 확장 후보에 남긴다.**

## Phase 개요

| ----- | -------------- | ------------------------------------ | ------------------------------------------------------------------- | -------------------------- | ------------------------------------------------------ |
| **1** | **은행 코어**  | —                                    | 가입 → 로그인 → 계좌 → 송금 → 거래내역                              | 없음                       | [domains/01-core.md](domains/01-core.md)               |
| 2     | 리스크 (FDS)   | 이체의 출금 평가 훅에 규칙을 꽂는다  | 송금 요청 → 규칙 평가 → 정상 / 보류(추가 인증) / 차단 → 관리자 확인 | 없음                       | [domains/02-risk.md](domains/02-risk.md)               |
| 3     | 여신/수신 상품 | 예금·대출 계좌가 입출금 계좌에 연결  | 적금 가입 → 자동이체 납입 → 만기 해지 / 대출 실행 → 원리금 상환     | 자동이체, 이자 계산, 연체  | [domains/03-product.md](domains/03-product.md)         |

| 5     | 카드           | 체크카드가 입출금 계좌에서 즉시 출금 | 결제 승인 → 계좌 출금 → 매입 → 가맹점 정산                          | 일마감 매입, 정산 지급     | [domains/05-card.md](domains/05-card.md)               |

| 7     | 보험           | 보험료가 은행 계좌에서 자동이체      | 청약 → 승인 → 보험료 납입 → 만기 환급 / 실효                        | 보험료 자동이체, 만기 도래 | [domains/07-insurance.md](domains/07-insurance.md)     |

순서의 근거는 의존성이다.

- **Phase 2(리스크)** 는 코어 바로 다음이다. 규칙 3~4개라 작고 배치가 필요 없다.
- **Phase 3(여신/수신 상품)** 이 Spring Batch·자동이체·영업일 캘린더를 처음 도입한다. 카드·증권·보험은 전부 이 인프라를 쓰므로 Phase 3 뒤에 온다.
- **Phase 4(오픈뱅킹)** 는 배치 의존이 없어 Phase 1 완료 후 어디에 두어도 된다.
- **Phase 5~7(카드·증권·보험)** 은 서로 독립이라 순서를 바꿔도 된다.

한 번에 한 Phase만 진행한다.

## 향후 확장 후보

지금 하지 않기로 한 것과 그 이유, 그리고 언제 다시 볼지를 적는다. "이것도 하자"가 나오면 먼저 이 표를 본다.

| 항목                                                       | 지금 하지 않는 이유                                                                                                   | 다시 볼 조건                                        |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| ML/DL 모델 기반 FDS                                        | 레이블된 실거래 데이터가 없어 학습·평가가 불가능하다. 룰 기반으로 시작한다.                                           | 룰 기반 `FdsAlert`가 쌓여 레이블 데이터가 생겼을 때 |
| 실제 외부 금융망 연동 (타행 이체, 실시간 시세, 오픈뱅킹망) | 인증·계약이 필요하다. 타행 계좌는 우리 DB의 다른 사용자 계좌로, 시세는 시드로, 오픈뱅킹은 "제공하는 쪽"으로 대체한다. | 이용기관 등록·시세 API 계약이 가능할 때             |
| 신용카드 청구 사이클                                       | Phase 5는 체크카드부터 시작한다. 이용일 → 매입 → 청구 마감 → 결제일의 월 단위 흐름은 그 다음이다.                     | Phase 5 완료 후                                     |
| 다중 통화                                                  | KRW부터 시작한다. `currency` 컬럼은 이미 있어 로직만 열면 된다.                                                       | 외화 계좌 요구가 생길 때                            |
| 프로덕션급 인프라 (k8s, CI/CD 파이프라인, 모니터링 스택)   | 배포는 Docker Compose + 서버 한 대로 시작한다.                                                                        | 서버 한 대로 부족해질 때                            |
| 시스템 상태 대시보드                                       | actuator 엔드포인트 노출로 시작한다.                                                                                  | 운영 중 지표를 화면으로 볼 필요가 생길 때           |
| 소셜 로그인, 이메일 인증 메일                              | 아래 "설계 전 결정 사항"에 따른다. 기본은 향후 후보.                                                                  | 설계 전 결정 사항에서 정한다                        |

## 설계 전 결정 사항

코어 DB 설계 전에 정하면 나중 비용이 크게 줄어드는 항목이다. 설계 뒤에 추가하면 마이그레이션 + API + 화면을 함께 고쳐야 한다.

| #   | 항목                           | 이 문서의 제안                                                                                            | 결정 |
| --- | ------------------------------ | --------------------------------------------------------------------------------------------------------- | ---- |
| 1   | 회원가입 시 수집 개인정보 범위 | 이메일·비밀번호·이름·휴대폰. 생년월일은 컬럼만 확보 — Phase 3 대출 심사, Phase 7 보험 청약에서 필요해진다 | ⬜   |
| 2   | 약관 동의 처리                 | Phase 1은 자리만. 동의 이력 테이블 자리를 확보 — Phase 4 오픈뱅킹 동의와 구조를 공유할 수 있다            | ⬜   |
| 3   | 이메일 인증 메일               | 향후 후보. 메일 인프라가 필요해 스코프가 크게 늘어남                                                      | ⬜   |
| 4   | 소셜 로그인                    | 향후 후보                                                                                                 | ⬜   |
| 5   | 관리자 계정·권한 구분          | **필요**. `role` 컬럼과 JWT claim에 포함. Phase 2가 쓴다                                                  | ⬜   |

결정되면 ⬜를 ✅로 바꾸고 결정 내용을 적는다.

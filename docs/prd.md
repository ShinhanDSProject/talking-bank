# talking-bank PRD

> 상태: 팀 검토용 초안
>
> 범위 기준: [MVP](./mvp.md) · 데이터 설계 참고: [ERD 초안](./erd.md) · 화면 토큰: [DESIGN.md](../DESIGN.md)
>
> 대화에서 합의한 기능을 사용자 흐름과 검증 가능한 요구사항으로 구체화한다. 합의하지 않은 수치·정책은 9절의 제안·미정 항목으로 구분하며, 이 문서 작성만으로 확정하지 않는다.

## 1. 목적과 개발 범위

사용자가 계좌 잔액 확인·송금·소비 분석을 위해 여러 메뉴를 찾아다니는 번거로움을 줄인다. PC 인터넷뱅킹의 일반 화면에 음성·텍스트 AI 챗봇을 함께 제공한다.

**말하면 알아듣고, 돈은 사람이 확인해야 움직이는 은행**을 구현한다. 챗봇은 요청을 이해하고 필요한 정보를 묻지만, 송금은 사용자 확인과 6자리 간편 비밀번호 검증 후에만 실행한다.

| 항목 | 내용 |
| --- | --- |
| 개발 기간 | 4주 |
| PM | 조성민 |
| AI | 김민석 |
| 백엔드 | 전민욱, 남윤재 |
| 프론트엔드 | 김예은, 이해진 |
| 서비스 환경 | PC 웹 우선, 일반 은행 화면과 AI 챗봇 함께 제공 |
| 금융 환경 | 실제 은행 이름을 사용하는 프로젝트 내부 가상 은행·계좌·자금 |

핵심 검증 목표는 가입부터 계좌 조회, 음성 송금 요청, 사람의 승인, 소비 분석까지 실제 저장 데이터로 연결되는 것이다. 아래 포함 기능은 모두 MVP 범위이며 일정상 제외가 필요하면 팀 합의로 MVP와 PRD를 함께 수정한다.

## 2. 사용자와 권한

| 대상 | 할 수 있는 일 |
| --- | --- |
| 비로그인 사용자 | 이메일 가입, 이메일·카카오·구글 로그인 |
| 일반 사용자 | 본인 계좌 개설·조회·충전·송금·결제, 소비 분석·분류 수정, 로그인 수단 연결, 본인 대화 관리 |
| 관리자 | 사용자·계좌·거래 조회, 가맹점 관리, 시연 데이터 생성 |
| 시연용 가상 인물 | 송금 대상 계좌의 소유자로 사용. 직접 로그인하는 사용자가 아님 |

다른 사용자 데이터는 일반 사용자에게 공개하지 않는다. 송금에 필요한 수취인 확인 정보만 제공하며, 수취 계좌의 잔액이나 전체 거래 내역은 제공하지 않는다. 관리자 권한은 화면 표시뿐 아니라 서버에서도 검증한다.

## 3. 화면과 입력 방식

| 화면 영역 | 제공 기능 |
| --- | --- |
| 가입·로그인 | 이메일 가입·로그인, 카카오·구글 로그인 |
| 계좌 조회 | 계좌 목록·잔액, 계좌 개설, 거래 내역, 가상 충전 |
| 이체 | 송금 입력·확인·완료, 저장한 수취 계좌와 별명 |
| 소비 분석 | 기간·카테고리별 합계·내역, 비교 차트, 거래별 분류 수정 |
| 가상 결제 | 결제할 계좌·가맹점·금액 선택 및 결과 |
| 사용자 설정 | 로그인 수단 연결, 송금용 PIN 설정, 기본 출금 계좌 |
| AI 챗봇 | 음성·텍스트 요청, 추가 질문, 결과 표시, 대화 목록·삭제 |
| 관리자 | 사용자·계좌·거래 조회, 가맹점·시연 데이터 관리 |

인터넷뱅킹 메뉴가 중심인 화면을 사용한다. 챗봇의 정확한 위치·크기와 화면 이름은 UI 설계에서 정한다. 조회·송금은 챗봇 없이 일반 화면으로도 가능해야 한다. 챗봇에 모든 관리 기능을 추가하는 것은 요구하지 않는다.

음성은 STT로 변환해 처리하며 답변은 텍스트·내역·차트로만 표시한다. 마이크를 사용할 수 없거나 권한을 거절해도 텍스트와 일반 화면을 계속 사용할 수 있어야 한다. 가상 서비스임을 화면에서 식별할 수 있게 한다.

## 4. 기능별 요구사항과 완료 조건

### 4.1 회원가입·로그인·연결

| ID | 요구사항 | 완료 조건 |
| --- | --- | --- |
| AUTH-01 | 이메일·비밀번호로 가입하고 로그인한다. | 가입한 정보로 로그인할 수 있고 중복 이메일·잘못된 인증 정보는 거절한다. |
| AUTH-02 | 카카오·구글 인증으로 가입·로그인한다. | 각 공급자로 가입 및 재로그인이 가능하고 동일 소셜 계정의 중복 사용자를 만들지 않는다. |
| AUTH-03 | 로그인한 계정에 다른 로그인 수단을 연결한다. | 연결 후 어떤 수단으로 접속하든 동일 사용자·계좌·대화가 조회된다. |
| AUTH-04 | 다른 사용자에게 연결된 로그인 수단을 가져오지 않는다. | 연결 충돌을 안내하고 기존 두 계정과 데이터를 유지한다. 이메일 일치만으로 자동 병합하지 않는다. |
| AUTH-05 | 송금용 6자리 간편 비밀번호를 별도로 설정한다. | 이메일·소셜 가입자 모두 설정할 수 있고 미설정 상태에서는 송금을 실행하지 않는다. |

흐름: 첫 가입 → 로그인 → 설정에서 로그인 수단 선택 → 해당 수단 인증 → 연결 완료. 소셜로 처음 가입한 사용자가 이메일 로그인을 추가할 때는 이메일 소유 확인과 비밀번호 설정이 필요하다. 구체적인 인증·복구 방식은 결정 항목으로 남긴다.

### 4.2 은행·계좌·충전·조회

| ID | 요구사항 | 완료 조건 |
| --- | --- | --- |
| ACC-01 | 사용자가 은행을 선택해 계좌를 만든다. | 한 사용자가 농협·국민·경남 등 여러 가상 은행의 계좌를 보유할 수 있다. |
| ACC-02 | 새 계좌에 샘플 거래 내역과 최종 잔액 100만 원을 제공한다. | 초기 입출금 합계, 내역의 잔액, 현재 잔액이 일치한다. |
| ACC-03 | 본인 계좌에 가상 돈을 충전한다. | 충전한 금액만큼 잔액이 증가하고 입금 내역이 남는다. 타인 계좌에 충전할 수 없다. |
| ACC-04 | 본인 계좌 목록·잔액·거래 내역을 조회한다. | 은행·계좌번호·잔액을 구분해서 보여주고 거래의 시각·유형·금액·입출금 방향을 확인할 수 있다. |
| ACC-05 | 거래 내역을 기간으로 조회한다. | 선택한 계좌·기간에 해당하는 내역을 보여주며 내역이 없으면 빈 상태를 표시한다. |

계좌가 없는 사용자는 개설 화면으로 이동할 수 있다. 샘플 내역을 제공하기 위해 과거 입금도 함께 구성하며, 초기 잔액에서 샘플 지출을 추가 차감해 100만 원보다 적게 시작하지 않는다.

### 4.3 송금·별명·기본 계좌

| ID | 요구사항 | 완료 조건 |
| --- | --- | --- |
| TRF-01 | 본인 계좌 간, 가입자 간, 시연용 가상 인물에게 송금한다. | 동일 은행·타행 모두 실행 가능하고 출금·입금 계좌에 함께 반영된다. |
| TRF-02 | 일반 화면과 음성·텍스트 챗봇으로 송금을 요청한다. | 어느 경로든 같은 확인·PIN 검증·실행 규칙을 거친다. |
| TRF-03 | 출금 계좌·수취 은행·계좌·이름·금액을 확인한다. | 사용자가 확인 화면에서 내용을 검토하고 6자리 PIN 검증에 성공한 뒤에만 실행된다. |
| TRF-04 | 확인 전에 내용을 수정하거나 취소한다. | 변경한 내용으로 다시 확인하며 취소한 요청은 잔액에 영향을 주지 않는다. |
| TRF-05 | 수취 계좌에 사용자 전용 별명을 지정한다. | “엄마에게 5만 원”처럼 요청하면 등록 계좌를 찾고 다른 사용자의 별명 설정에 영향을 주지 않는다. |
| TRF-06 | 기본 출금 계좌를 지정한다. | 명시한 계좌가 있으면 우선 사용하고 없으면 기본 계좌를 제시한다. 최종 확인 전 변경할 수 있다. |
| TRF-07 | 실패·동시 요청·중복 요청에도 금액을 정확히 처리한다. | 실패로 한쪽만 반영되지 않고 동일 송금 재시도로 중복 차감되지 않는다. |

수취 은행·계좌번호로 실제 프로젝트 내부 계좌를 확인한다. 이름이나 별명으로 후보가 여러 개면 선택을 요청하고 임의로 한 명에게 보내지 않는다. 출금 계좌가 결정되지 않으면 본인 계좌 중 선택을 요청한다. 출금·입금이 같은 계좌인 요청은 거절한다.

송금 성공은 서버의 완료 결과로 판단한다. 통신이 끊겨 결과를 모르는 경우 실패로 단정하거나 새 송금을 자동 실행하지 않고 기존 요청 결과를 조회한다.

### 4.4 가상 결제

| ID | 요구사항 | 완료 조건 |
| --- | --- | --- |
| PAY-01 | 별도 가상 결제 화면에서 계좌·가맹점·금액을 선택한다. | 선택 내용을 확인하고 결제를 실행하면 해당 계좌에서 차감된다. |
| PAY-02 | 결제 거래와 카테고리를 기록한다. | 거래 내역에 결제가 표시되고 가맹점 기본 카테고리로 소비 분석에 반영된다. |
| PAY-03 | 유효하지 않은 결제를 차단한다. | 잔액 부족·잘못된 금액·사용 불가 계좌나 가맹점이면 차감하지 않으며 중복 실행으로 재차감하지 않는다. |

가상 결제는 사용자에게 제공하는 화면이다. 관리자 전용 시연 버튼으로 대체하지 않는다. 결제 시 추가 PIN 인증 여부는 송금 인증과 별도로 미정이다.

### 4.5 소비 분류·분석

| ID | 요구사항 | 완료 조건 |
| --- | --- | --- |
| EXP-01 | 기간·카테고리별 소비 합계와 내역을 제공한다. | 저장된 완료 거래에서 계산한 합계와 상세 내역의 합이 일치한다. |
| EXP-02 | 샘플 거래와 새 거래를 함께 분석한다. | 새 결제·송금이 완료되면 다음 조회 결과에 반영된다. |
| EXP-03 | 타인 송금을 미분류 소비로 기록한다. | 전체 소비에는 포함되고 특정 카테고리 합계에는 들어가지 않는다. |
| EXP-04 | 사용자가 거래별 분류를 지정·변경한다. | 미분류 송금과 자동 분류 결제 모두 수정 가능하고 통계·차트가 갱신된다. |
| EXP-05 | 두 기간의 소비를 비교한다. | 각 기간·소비액·증감액·증감률과 비교 차트를 표시한다. |

| 거래 종류 | 소비 포함 여부 |
| --- | --- |
| 가맹점 결제 출금 | 포함, 가맹점 기준 자동 분류 |
| 다른 사람에게 송금한 출금 | 포함, 최초 미분류 |
| 본인 계좌 간 이체 | 제외 |
| 가상 충전·초기 자금·받은 송금 | 제외 |
| 실패·취소·미완료 요청 | 제외 |

분류 수정은 해당 거래의 분석 기준만 변경한다. 송금액·잔액·다른 거래·가맹점 기본 분류는 유지한다. 현재 카테고리 기준으로 과거 기간을 다시 조회하며, 이미 저장된 챗봇 답변을 자동 재작성할지는 9절에서 다룬다.

### 4.6 챗봇·STT·대화 관리

| ID | 요구사항 | 완료 조건 |
| --- | --- | --- |
| AI-01 | 음성과 텍스트로 조회·송금 요청·소비 분석을 제공한다. | 동일한 의도의 두 입력 방식이 같은 업무 기능으로 연결된다. |
| AI-02 | 부족하거나 모호한 정보를 추가 질문한다. | “엄마한테 보내줘” 다음 “5만 원”을 앞선 요청과 연결하며 미확정 계좌·금액을 추측해 실행하지 않는다. |
| AI-03 | 응답에 서버의 실제 조회·계산 결과를 사용한다. | AI가 잔액·소비액·송금 성공 여부를 만들어내지 않는다. 결과를 받지 못하면 실패 또는 확인 중임을 알린다. |
| AI-04 | 대화를 저장하고 다시 보거나 새로 시작한다. | 본인 대화만 조회되며 새 대화에 이전의 미완료 송금이 자동 실행되지 않는다. |
| AI-05 | 대화를 삭제한다. | 삭제한 대화는 목록·조회에서 사라지지만 계좌 잔액과 금융 기록은 유지된다. |
| AI-06 | 음성·AI 기능 실패 시 대체 경로를 제공한다. | 마이크 거부·인식 실패·AI 오류를 안내하고 텍스트 재입력 또는 일반 화면 이용이 가능하다. |

금액·계좌번호·별명 인식 결과는 최종 확인 화면에서 확인할 수 있어야 한다. PIN은 챗봇에 말하거나 적게 하지 않고 전용 입력 화면에서 받는다. 명령으로 권한 검증·확인·인증을 생략할 수 없다. 대화 삭제로 미완료 송금도 더 이상 실행되지 않게 하되 완료 거래는 유지한다.

### 4.7 관리자

| ID | 요구사항 | 완료 조건 |
| --- | --- | --- |
| ADM-01 | 사용자와 계정 상태를 조회한다. | 관리자만 조회 가능하고 비밀번호·PIN·토큰은 노출하지 않는다. |
| ADM-02 | 계좌·송금·결제·충전 내역을 조회한다. | 사용자·계좌·거래 관계와 처리 결과를 확인할 수 있다. |
| ADM-03 | 가맹점을 등록하고 업종·기본 카테고리를 설정한다. | 새 결제에 설정이 적용되며 과거 사용자 분류를 덮어쓰지 않는다. |
| ADM-04 | 가상 인물·계좌·샘플 거래를 생성한다. | 생성 데이터로 송금·분석을 시연할 수 있고 잔액과 기록이 일치한다. |

사용자 차단·잔액 직접 수정·금융 기록 삭제 기능은 현재 합의한 관리자 범위에 자동 포함하지 않는다. 샘플 생성도 일반 사용자가 관리자 요청으로 위장해 실행할 수 없어야 한다.

## 5. 주요 사용자 흐름

### A. 가입과 로그인 수단 연결

첫 가입 → 동일 사용자 계정 생성 → 로그인 → 설정에서 다른 로그인 수단 인증·연결 → 로그아웃 후 연결한 수단으로 로그인 → 기존 계좌·대화 확인.

### B. 계좌 개설과 송금

은행 선택 → 계좌 개설 → 초기 잔액 100만 원·샘플 내역 확인 → PIN·기본 출금 계좌·수취 별명 설정 → 일반 화면 또는 챗봇 송금 요청 → 누락 정보 질문 → 수취 정보 및 출금 계좌 확인 → PIN 검증 → 실행 결과·갱신된 잔액 확인.

### C. 결제와 소비 분석

가상 결제 화면에서 계좌·가맹점·금액 선택 → 결제 → “이번 달 식비 얼마 썼어?” → 합계·내역 확인 → “지난달과 비교해줘” → 기간 비교·차트 확인 → 거래 분류 수정 → 분석 화면에서 갱신 결과 확인.

### D. 운영 시연 준비

관리자 로그인 → 가맹점·카테고리 설정 → 가상 인물·계좌 생성 → 샘플 거래 추가 → 계좌·거래 내역과 잔액 검증 → 일반 사용자 화면에서 송금·분석 시연.

## 6. 공통 업무 규칙과 오류 처리

| 상황 | 기대 동작 |
| --- | --- |
| 로그인 만료·접근 권한 없음 | 인증 또는 접근 제한 안내. 금융 처리를 실행하지 않음 |
| 소셜 인증 취소·실패 | 가입·연결이 완료된 것처럼 표시하지 않고 다시 시도 가능 |
| 계좌·가맹점·금액이 유효하지 않음 | 원인과 수정할 항목을 안내하고 차감하지 않음 |
| PIN 미설정·오류·잠금 | 송금 실행 차단. 설정 또는 정해진 복구 경로 안내 |
| 확인 이후 금액·수취 계좌 변경 | 기존 확인을 무효화하고 변경 내용을 다시 확인 |
| 잔액 부족·동시 출금 | 실행 시점 잔액으로 검증하고 잔액이 음수가 되지 않음 |
| 버튼 중복 클릭·응답 유실 | 같은 요청의 처리 결과를 확인하며 중복 차감하지 않음 |
| STT 인식 실패·모호한 요청 | 재입력·추가 질문 제공. 임의 송금 금지 |
| 소비 데이터 없음 | 0원 또는 빈 내역으로 표시. 오류나 가공 거래를 생성하지 않음 |

금융 작업과 잔액·거래 기록은 함께 성공하거나 함께 실패해야 한다. 사용자 소유권과 관리자 권한은 서버 기준으로 검증한다. 분석은 완료된 거래만 대상으로 하고 AI의 계산 결과를 원장 대신 사용하지 않는다.

## 7. 품질·검증 기준

- PC에서 주요 메뉴·입력·확인·결과를 읽고 조작할 수 있고 마이크 없이도 핵심 업무를 완료할 수 있다.
- 화면 디자인 토큰은 DESIGN.md를 따른다. 해당 문서에 남은 인증서 로그인·음성 되읽기 등 이전 기획을 신규 기능으로 포함하지 않는다.
- 비밀번호·PIN·토큰은 로그·대화·일반 조회 응답에 노출하지 않는다.
- 로그인 수단 연결과 소유권·권한 제한, 실패·중복·동시 금융 요청의 정합성을 검증한다.
- 핵심 흐름 A~D를 준비된 가상 데이터로 확인하며, 실행 결과를 화면과 저장 데이터 양쪽에서 대조한다.
- API·웹의 프로젝트 검증 명령인 `npm test`, `npm run lint`, `npm run typecheck`를 구현 PR에서 실행하고 결과를 기록한다.
- 응답시간·STT 정확도·동시 사용자 수의 수치 목표는 측정 조건과 함께 팀이 정한다. 근거 없는 달성 수치를 기재하지 않는다.

## 9. 팀 결정이 필요한 세부 정책

아래는 구현 전 검토할 제안이며 합의된 기능 범위를 임의로 축소하거나 확대하지 않는다. 채택한 정책은 관련 요구사항과 ERD에 함께 반영한다.

| 항목 | 제안 또는 결정할 내용 |
| --- | --- |
| 가입 정보·인증 | 필수 이름·전화번호 여부, 이메일 인증 방식, 비밀번호 정책·복구 방법 결정 |
| 계정 연결 | 공급자별 한 계정 연결 제안. 연결 해제와 이미 별도 가입한 계정의 병합은 별도 결정 |
| 로그인 세션 | 기존 refresh_token 구조와 로그아웃·만료·회전·다중 기기 정책 확인 |
| PIN | 실패 허용 횟수·잠금 시간·재설정 수단 결정. DESIGN.md의 기존 횟수를 확정값으로 간주하지 않음 |
| 송금·충전 | 수수료 0원·원화 정수 금액만 허용하는 방안 제안. 건별·일별 한도, 충전 단위 결정 |
| 확인 유효기간 | 송금 확인 만료 시간 및 만료 후 재입력 범위 결정 |
| 계좌 상태 | 기존 ACTIVE·DORMANT·CLOSED 중 거래 허용 상태와 상태 변경 기능 범위 결정 |
| 별명 | 중복 허용 후 선택 요청 제안. 이름·은행만으로 여러 계좌가 검색되면 선택 요청 |
| 소비 카테고리 | 식비·카페/간식·교통·쇼핑·생활·문화/여가·기타를 초기 후보로 제안. 미분류와 기타 구분 |
| 소비 기간·계좌 | 한국 시간 기준 월 단위, 기본은 본인 전체 계좌 합산 제안. 특정 계좌 요청은 해당 계좌만 조회 |
| 기간 비교 | 이번 달 현재까지와 지난달 전체를 비교할 경우 실제 시작·종료일을 명시하는 방안 제안. 동일 경과일 비교 여부 결정 |
| 증감률 | `(현재-이전)/이전×100`. 이전 금액이 0이면 비율은 표시하지 않고 금액과 비교 불가 안내 제안 |
| 샘플 데이터 | 비교가 가능한 과거 월 포함 제안. 기간·건수·기존 계좌 추가 생성 방식 결정 |
| 결제 인증 | 결제에 PIN을 추가할지 결정. 송금 PIN 필수 요구사항과 구분 |
| 대화 데이터 | 음성 원본은 저장하지 않고 STT 텍스트만 저장하는 방안 제안. 보존 기간·삭제 방식 결정 |
| 과거 답변 | 저장 답변은 조회 당시 결과로 표시하고 새 질문·분석 화면은 최신 분류로 계산하는 방안 제안 |

## 10. 문서 간 반영과 후속 작업

- MVP는 포함·제외 범위를, PRD는 사용자에게 제공할 동작과 완료 조건을, ERD는 저장 구조와 제약을 설명한다.
- 기존 ERD는 팀장님 스크린샷을 참고한 초안이며 PR 원문 전체와의 대조는 아직 필요하다. ERD의 제안이 본 문서의 정책을 자동 확정하지 않는다.
- 이 PR은 PRD만 추가한다. ERD의 “PRD 작성 전” 표기와 미정 정책은 본 PRD 검토 이후 별도 수정에서 정합성을 맞춘다.
- 팀 검토 후 기능 ID를 기준으로 구현 이슈와 API 명세를 작성하고, 결정된 정책을 ERD·화면 설계에 반영한다.

# 05. 4주 일정

## 시간 예산

먼저 현실을 계산한다. 팀 6명 기준.

```
4주 × 5일 × 8시간                    = 160시간/인, 960 인시
- 4주차는 통합·버그·발표 준비        → 기능 개발은 실질 3주
- 회의·설계·코드 리뷰·학습           → 초심자는 40~50%가 여기 쓰임
────────────────────────────────────────────────────────────
실제 기능 개발에 쓰이는 시간          ≈ 350~450 인시
```

초심자 팀은 환경 설정, git 충돌, 에러 디버깅에 예상의 2~3배가 든다. 그래서 **P0가 끝나기 전에 P1을 시작하지 않는다.**

## 원칙: 1주차에 끝까지 관통하는 한 줄

초심자 팀이 무너지는 가장 흔한 패턴은 각자 자기 파트만 만들다가 마지막 주에 합치면서 터지는 것이다. 이를 막기 위해 **1주차 안에 로그인 → API → 화면 → 배포가 작게라도 한 번 돌아가야 한다.** 그 뒤로는 기능을 얹기만 하면 된다.

### 2주차 — 송금

목표: **송금이 동시성까지 정확히 동작한다.** 이 프로젝트의 심장.

| 영역   | 할 일                                                                           |
| ------ | ------------------------------------------------------------------------------- |
| 백엔드 | Transfer·Transaction 엔티티, 송금 API (트랜잭션·비관적 락·멱등성)               |
| 백엔드 | 동시성 테스트, 롤백 테스트 — [02-scope.md XFER AC](02-scope.md#xfer--송금) 전부 |
| 백엔드 | 거래내역 조회 API (페이지네이션, 기간 필터)                                     |
| 백엔드 | 공통 에러 응답·예외 처리 (#24), Swagger (#25)                                   |
| 프론트 | 송금 화면 (입력 → 수취인 확인 → 실행 → 결과), 거래내역 화면                     |
| 프론트 | API 에러 코드에 따른 메시지 표시 공통화                                         |
| FDS    | 규칙 설계 확정 (어떤 규칙, 임계값, 보류/차단 기준). 코드는 3주차                |

**2주차 끝 체크**: 두 계정으로 로그인해 서로 송금하고, 양쪽 거래내역에 남는 것을 본다. 동시성 테스트가 통과한다.

### 3주차 — FDS와 관리자

목표: **의심 거래가 잡히고, 관리자가 그것을 본다.**

| 영역   | 할 일                                                                       |
| ------ | --------------------------------------------------------------------------- |
| 백엔드 | FDS 규칙 3~4개 구현, 송금 흐름에 연결, FdsAlert 기록                        |
| 백엔드 | 보류(PENDING_AUTH) → 추가 인증 → 완료 흐름                                  |
| 백엔드 | 관리자 API — 이상거래 목록·상세, 거래 로그. `ROLE_ADMIN` 인가               |
| 프론트 | 송금 결과에 보류·차단 케이스 추가, 추가 인증 화면                           |
| 프론트 | 관리자 화면 — 이상거래 목록, 거래 로그 (읽기 전용)                          |
| 공통   | **AI 기능 결정** — 할지, 무엇을, Dify인지 직접 구현인지. 결정 못 하면 안 함 |

**3주차 끝 체크**: 고액 송금을 시도하면 보류되고, 관리자 화면에 뜬다. 시연 시나리오가 처음부터 끝까지 한 번 돈다.

### 4주차 — 마무리

목표: **끊기지 않는 시연, 설명할 수 있는 코드.**

| 할 일                                                                      |
| -------------------------------------------------------------------------- |
| 시연 시나리오 반복 실행, 발견되는 버그 수정. **새 기능 추가 금지**         |
| P2 중 하나 (여유 있을 때만): AI 설명 생성 or 자동이체                      |
| 예외 케이스 정리 — 잔액 부족, 만료 토큰, 존재하지 않는 계좌, 네트워크 오류 |
| README·docs 최신화, 발표 자료, 데모 영상 백업                              |
| 회고 — 잘 된 것, 안 된 것, 다시 한다면                                     |

4주차 월요일부터는 **main에 기능 PR을 머지하지 않는다.** 버그 수정만.

## 시연 시나리오

발표에서 보여줄 흐름. 3주차부터 이 순서대로 매일 한 번 돌려본다.

1. 회원가입 → 로그인
2. 내 계좌와 잔액 확인
3. 다른 회원에게 소액 송금 → 성공 → 양쪽 거래내역 확인
4. 잔액보다 큰 금액 송금 → 거절
5. 고액 송금 → FDS 보류 → 추가 인증 → 완료
6. (있다면) 단시간 반복 송금 → 차단
7. 관리자 로그인 → 이상거래 목록에서 5·6번 확인 → 거래 로그
8. (P2 완료 시) AI 설명 or 자동이체 시연

# 05. 진행 순서

> 이 문서는 **날짜를 적지 않는다.** Phase와 그 안의 Step, 각각의 완료 조건만 정의한다. 날짜는 팀 회의에서 정해 GitHub 마일스톤에 붙인다.

## 원칙

1. **Phase는 순서대로, 하나씩.** 앞 Phase의 완료 조건을 만족하기 전에 다음 Phase를 시작하지 않는다.
2. **Step 1-1에서 끝까지 관통하는 한 줄을 만든다.** 가장 먼저 로그인 → API → 화면 → 배포가 작게라도 한 번 돌아가게 하고, 그 뒤에 기능을 얹는다.
3. **완료 조건은 "누가 봐도 확인 가능한 것"으로 쓴다.** "송금 구현"이 아니라 "동시성 테스트가 통과한다".
4. **Step을 놓치면 다음 Step에서 뺀다. 밀지 않는다.**
5. **발표 전 마지막 Step은 항상 "마무리"다.** 새 기능을 넣지 않고, 시연 시나리오를 반복해 돌리며 버그만 잡는다.

## Phase 1 — 은행 코어

### Step 1-1 — 기반 구축

목표: **로그인해서 내 계좌 목록이 보인다.** 배포된 주소에서.

| 영역   | 할 일                                                                                                                   |
| ------ | ----------------------------------------------------------------------------------------------------------------------- |
| 공통   | 컨벤션·인증 정책·응답 포맷 확정. [코어 설계 전 결정 사항 5개](02-scope.md#미확정-스코프--지금-결정해야-하는-것) 답 받기 |
| 공통   | Spring Boot 3.5.x 전환 머지 (PR #28)                                                                                    |
| 백엔드 | User 엔티티(`role` 포함), 회원가입·로그인·토큰 재발급 API, Security 설정                                                |
| 백엔드 | Account에 User 연관·`accountType` 추가, 내 계좌 목록 API를 인증 기반으로                                                |
| 프론트 | 폴더 구조 확정, 디자인 시스템 기본(색·타이포·버튼·입력), 로그인·가입 화면                                               |
| 프론트 | 로그인 후 계좌 목록 화면 (이미 있는 화면에 인증 연결)                                                                   |
| 인프라 | docker-compose에 Redis 추가(확정 시), 서버 1대에 배포 스크립트                                                          |

**완료 조건**: 팀원 전원이 배포 주소에서 가입 → 로그인 → 계좌 목록을 본다.

### Step 1-2 — 송금과 거래내역

목표: **송금이 동시성까지 정확히 동작한다.**

| 영역   | 할 일                                                                                             |
| ------ | ------------------------------------------------------------------------------------------------- |
| 백엔드 | Transfer·Transaction 엔티티(`sourceType` 포함), 송금 API (트랜잭션·비관적 락·멱등성·출금 평가 훅) |
| 백엔드 | 동시성 테스트, 롤백 테스트 — [02-scope.md XFER AC](02-scope.md#xfer--송금) 전부                   |
| 백엔드 | 거래내역 조회 API (페이지네이션, 기간 필터)                                                       |
| 백엔드 | 공통 에러 응답·예외 처리, Swagger                                                                 |
| 프론트 | 송금 화면 (입력 → 수취인 확인 → 실행 → 결과), 거래내역 화면                                       |
| 프론트 | API 에러 코드에 따른 메시지 표시 공통화                                                           |

**완료 조건**: 두 계정으로 로그인해 서로 송금하고, 양쪽 거래내역에 남는 것을 본다. 동시성·롤백·멱등성 테스트가 통과한다.

### Step 1-3 — 안정화

목표: **끊기지 않는 시연, 설명할 수 있는 코드.**

- 시연 시나리오 반복 실행, 발견되는 버그 수정. **새 기능 추가 금지**
- 예외 케이스 정리 — 잔액 부족, 만료 토큰, 존재하지 않는 계좌, 네트워크 오류
- README·docs 최신화
- 회고 — 잘 된 것, 안 된 것, 다시 한다면

**완료 조건**: [01-overview.md 성공 기준](01-overview.md#성공-기준) 전부 체크.

> Phase 1이 프로젝트의 마지막 Phase라면 Step 1-3이 발표 전 마무리다(발표 자료·데모 영상 백업 포함). Phase 2 이상을 진행한다면 Step 1-3은 짧게 끝내고, 마무리 Step은 마지막 Phase 끝에 둔다.

## Phase 2 이후

각 Phase는 같은 모양이다: **진입 조건 → 설계 → 구현 → 안정화 → 완료 조건.** 상세 Step은 그 Phase에 착수할 때 쓴다.

| Phase | 도메인         | 진입 조건    | 핵심 산출물                                                                         | 완료 조건                                                                |
| ----- | -------------- | ------------ | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 2     | 리스크 (FDS)   | Phase 1 완료 | 규칙 3~4개, 보류(추가 인증)·차단 흐름, `FdsAlert`, 관리자 이상거래·거래 로그 화면   | 고액 송금이 보류되고 추가 인증 후 완료된다. 차단 건이 관리자 화면에 뜬다 |
| 3     | 여신/수신 상품 | Phase 2 완료 | 적금 가입·만기, 대출 실행·원리금 상환, **Spring Batch·자동이체·영업일 캘린더 도입** | 적금 자동 납입 배치가 돌고, 만기 시 이자 포함 지급이 거래내역에 남는다   |
| 4     | 오픈뱅킹       | Phase 1 완료 | OAuth 2.0 인가 서버, 동의 화면, 계좌 조회·이체 오픈 API                             | 가상 외부 앱이 OAuth로 동의를 받아 계좌를 조회하고 이체한다              |
| 5     | 카드           | Phase 3 완료 | 체크카드 승인 → 계좌 출금(FDS 훅 통과), 매입, 가맹점 정산 배치                      | 결제 승인이 계좌 잔액을 줄이고, 일마감 배치가 가맹점별 정산액을 만든다   |
| 6     | 증권           | Phase 3 완료 | 예수금 이체, 가상 매수/매도, T+2 결제 배치, 포트폴리오 평가                         | 매수 체결 2영업일 뒤 결제 배치가 돌고, 평가액이 갱신된다                 |
| 7     | 보험           | Phase 3 완료 | 청약·자동 심사, 보험료 자동이체, 만기·실효 배치                                     | 보험료 미납 시 실효 배치가 돌고, 부활 시 미납분이 정산된다               |

- Phase 4(오픈뱅킹)는 배치 의존이 없어 Phase 1 뒤 어디에 두어도 된다.
- Phase 5~7은 서로 독립이라 순서를 바꿔도 된다. 단, 전부 Phase 3의 배치 인프라를 쓴다.
- **동시에 두 Phase를 진행하지 않는다.**

## 시연 시나리오

Step 1-2부터 이 순서대로 매일 한 번 돌려본다. 완료한 Phase마다 장면을 덧붙인다.

**Phase 1**

1. 회원가입 → 로그인
2. 내 계좌와 잔액 확인
3. 다른 회원에게 송금 → 성공 → 양쪽 거래내역 확인
4. 잔액보다 큰 금액 송금 → 거절
5. 같은 송금 버튼 연타 → 한 번만 이체됨

**Phase 2**

6. 고액 송금 → FDS 보류 → 추가 인증 → 완료
7. 단시간 반복 송금 → 차단
8. 관리자 로그인 → 이상거래 목록에서 6·7번 확인 → 거래 로그

**Phase 3 이후** — 예: 적금 가입 → (배치 실행) → 납입 내역이 거래내역에 찍힘.

# 01. 프로젝트 개요

> 이 문서는 프로젝트의 "왜"와 "무엇"을 한 장으로 정리한다. 범위·스펙·일정의 세부는 다른 문서를 본다.

## 한 줄 정의

**계좌와 송금을 중심으로, 이상거래 탐지까지 갖춘 은행 서비스** — 4주 안에 "송금이 동시성까지 고려해 정확히 동작하는" 결과물을 만든다.

## 배경

신한 SW 아카데미 금융공학 스터디에서 다룬 6개 금융 도메인(은행 여신/수신, 카드 결제/정산, 증권/투자, 리스크 & 컴플라이언스, 핀테크 & 오픈뱅킹, 보험) 중 **은행 시스템**을 주제로 골랐다.

이유는 세 가지다.

1. **요구사항을 설명할 필요가 없다.** 계좌·송금·거래내역은 팀원 전원이 이미 사용자로서 안다. 기획 논쟁 없이 구현에 들어갈 수 있다.
2. **난이도 계단이 자연스럽다.** 계좌 조회(CRUD) → 송금(트랜잭션) → 동시 출금(락) → 이상거래 탐지(룰 엔진) → 자동이체(배치) 순으로 실력에 맞춰 올라갈 수 있고, 어디서 멈춰도 결과물이 남는다.
3. **여기서 배우는 것이 진짜다.** 돈 계산(`BigDecimal`), 트랜잭션 원자성, 동시성 제어, 멱등성은 게시판·쇼핑몰 프로젝트로는 만나기 어렵다.

스터디 자료에서 직접 가져오는 부분은 **1팀(은행 여신/수신)** 의 계좌·이체 흐름과 **4팀(리스크 & 컴플라이언스)** 의 FDS 실시간 룰 + 배치 이중 구조다.

## 목표

### 산출물 목표

- 회원이 가입·로그인하고, 자기 계좌를 조회하고, 다른 계좌로 송금하고, 거래내역을 확인할 수 있다.
- 송금은 **동시 요청에도 잔액이 음수가 되지 않고**, 출금과 입금이 함께 성공하거나 함께 실패한다.
- 룰 기반 FDS가 의심 거래를 탐지해 차단하거나 보류하고, 관리자가 그 목록을 볼 수 있다.
- 로컬에서 `npm run dev` 한 번으로 전체가 뜨고, 시연 시나리오가 처음부터 끝까지 돌아간다.

### 학습 목표

- 금액을 다루는 코드에서 `double`을 쓰면 안 되는 이유를 직접 겪고 설명할 수 있다.
- `@Transactional`의 경계와 롤백을 송금 코드로 설명할 수 있다.
- 같은 계좌에 동시 출금이 들어올 때 무엇이 잘못되고 어떻게 막는지 설명할 수 있다.
- 실시간 룰 탐지와 배치 분석이 왜 둘 다 필요한지 설명할 수 있다.
- 이슈 → 브랜치 → PR → 리뷰 → 머지의 협업 흐름을 몸에 익힌다.

## 성공 기준

프로젝트가 끝났을 때 아래를 모두 만족하면 성공이다. 기능 개수가 아니라 **핵심 기능의 완성도**로 판단한다.

- [ ] 시연 시나리오(가입 → 로그인 → 계좌 확인 → 송금 → 거래내역 → 이상거래 차단 → 관리자 확인)가 끊기지 않고 돌아간다.
- [ ] 같은 계좌에 동시 출금 요청을 보내는 테스트가 있고, 잔액이 음수가 되지 않음을 증명한다.
- [ ] 송금 도중 실패 시 출금만 되고 입금이 안 되는 경우가 없음을 테스트로 증명한다.
- [ ] 백엔드·프론트엔드 테스트가 CI 없이도 `npm test` 한 번으로 통과한다.
- [ ] 팀원 전원이 "송금이 어떻게 동작하는지"를 자기 말로 설명할 수 있다.

# 01. 프로젝트 개요

> 이 문서는 프로젝트가 무엇을 만드는지 한 장으로 정리한다. 범위·스펙·일정의 세부는 다른 문서를 본다.

## 한 줄 정의

**하나의 은행 계좌를 중심으로 6개 금융 도메인이 연결된 시스템** — 은행 코어(계좌·이체·거래)를 먼저 깊게 만들고, 그 위에 여신/수신 상품, 오픈뱅킹, 카드, 증권, 보험을 단계적으로 쌓는다.

## 배경

신한 SW 아카데미 금융공학 스터디에서 6개 금융 도메인을 배웠다.

| 도메인                | 핵심                                    |
| --------------------- | --------------------------------------- |
| 은행 여신/수신        | 계좌 · 이체 · 예금 · 대출 · 이자 · 연체 |
| 카드 결제/정산        | 승인 · 매입 · 정산 · 청구 사이클        |
| 증권/투자             | 주문 · 체결 · T+2 결제 · 포트폴리오     |
| 리스크 & 컴플라이언스 | FDS · AML · 이상거래 탐지               |
| 핀테크 & 오픈뱅킹     | OAuth · 오픈 API · 마이데이터 · 토큰화  |
| 보험                  | 보험료 · 언더라이팅 · 만기 · 실효/부활  |

이 6개는 따로 노는 시스템이 아니다. **전부 은행 계좌에 연결되어 있다.** 카드 결제는 계좌에서 출금되고, 증권 매수 대금은 계좌에서 빠지고, 보험료는 계좌에서 자동이체되고, 오픈뱅킹은 그 계좌를 외부 앱에 노출하고, FDS는 이 모든 거래를 감시한다.

그래서 프로젝트를 이렇게 잡는다.

```
                    ┌─ 여신/수신 상품   예금·대출이 계좌에 붙는다
                    ├─ 오픈뱅킹        계좌 조회·이체 API를 OAuth로 외부에 연다
은행 코어 ──────────┼─ 카드            체크카드 승인 → 계좌 출금 → 가맹점 정산
계좌 · 이체 · 거래  ├─ 증권            계좌 연동 매수 → T+2 결제
                    ├─ 보험            보험료 자동이체 → 만기 처리
                    └─ FDS             모든 거래를 감시한다
```

**은행 코어를 Phase 1로 먼저 만들고, 나머지 도메인을 Phase 2 이후에 하나씩 얹는다.** 각 도메인은 코어와 연결되는 핵심 흐름 하나씩만 구현하고, 어느 Phase에서 멈춰도 동작하는 결과물이 남는다. Phase 순서와 범위는 [02-scope.md](02-scope.md), 진행 순서는 [05-schedule.md](05-schedule.md)에 있다.

## 목표

### 산출물 목표

**Phase 1 (은행 코어)** — 반드시 달성한다.

- 회원이 가입·로그인하고, 자기 계좌를 조회하고, 다른 계좌로 송금하고, 거래내역을 확인할 수 있다.
- 송금은 **동시 요청에도 잔액이 음수가 되지 않고**, 출금과 입금이 함께 성공하거나 함께 실패한다.
- 룰 기반 FDS가 의심 거래를 탐지해 차단하거나 보류하고, 관리자가 그 목록을 볼 수 있다.
- 로컬에서 `npm run dev` 한 번으로 전체가 뜨고, 시연 시나리오가 처음부터 끝까지 돌아간다.

**Phase 2 이후** — 코어 위에 도메인을 하나씩 얹는다. 각 Phase의 완료 조건은 [05-schedule.md](05-schedule.md)에 있다.

### 학습 목표

- 금액을 다루는 코드에서 `double`을 쓰면 안 되는 이유를 직접 겪고 설명할 수 있다.
- `@Transactional`의 경계와 롤백을 송금 코드로 설명할 수 있다.
- 같은 계좌에 동시 출금이 들어올 때 무엇이 잘못되고 어떻게 막는지 설명할 수 있다.
- 실시간 룰 탐지와 배치 분석이 왜 둘 다 필요한지 설명할 수 있다.
- 정해진 시점에 돌아야 하는 일(정산·결제·만기)을 Spring Batch로 어떻게 처리하는지 설명할 수 있다. (Phase 2 이후)
- 6개 금융 도메인이 계좌를 중심으로 어떻게 이어지는지 자기 말로 설명할 수 있다.
- 이슈 → 브랜치 → PR → 리뷰 → 머지의 협업 흐름을 몸에 익힌다.

## 성공 기준

프로젝트가 끝났을 때 아래를 모두 만족하면 성공이다. 기능 개수가 아니라 **코어의 완성도**로 판단한다.

- [ ] 시연 시나리오(가입 → 로그인 → 계좌 확인 → 송금 → 거래내역 → 이상거래 차단 → 관리자 확인)가 끊기지 않고 돌아간다.
- [ ] 같은 계좌에 동시 출금 요청을 보내는 테스트가 있고, 잔액이 음수가 되지 않음을 증명한다.
- [ ] 송금 도중 실패 시 출금만 되고 입금이 안 되는 경우가 없음을 테스트로 증명한다.
- [ ] 백엔드·프론트엔드 테스트가 `npm test` 한 번으로 통과한다.
- [ ] 팀원 전원이 "송금이 어떻게 동작하는지"와 "6개 도메인이 계좌로 어떻게 이어지는지"를 자기 말로 설명할 수 있다.

Phase 2 이상을 완료했다면 그만큼 추가 달성이다. Phase 1이 불완전한 채 Phase 2를 시작한 것은 성공이 아니다.

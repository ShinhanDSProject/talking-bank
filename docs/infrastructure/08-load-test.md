# Talking Bank 부하 테스트 계획

> 상태: 학습 및 초기 검증 계획. 운영 시스템과 실제 고객 데이터에는 직접 수행하지 않는다.

## 1. 목적

- 현재 시스템이 어느 정도의 요청을 처리할 수 있는지 측정한다.
- 응답시간이 느려지는 지점을 찾는다.
- API, ECS, JVM, DB 중 병목 계층을 구분한다.
- 자동 확장과 장애 복구가 의도대로 작동하는지 확인한다.

## 2. 용어

| 용어 | 의미 |
| --- | --- |
| VU | 동시에 행동하는 가상 사용자 |
| RPS/TPS | 초당 요청 수/초당 처리 건수 |
| Latency | 요청부터 응답까지 걸린 시간 |
| p95 | 전체 요청의 95%가 이 시간 이내에 끝난다는 값 |
| Error Rate | 전체 요청 중 실패한 비율 |
| Throughput | 일정 시간 동안 성공적으로 처리한 작업량 |
| Bottleneck | 전체 성능을 제한하는 가장 느린 지점 |

금융 프로젝트에서 TPS는 단순 HTTP 요청 수와 실제 성공 거래 수를 구분해서 기록한다.

## 3. 도구 제안

첫 도구로 k6를 제안한다.

- JavaScript로 시나리오를 작성할 수 있다.
- CI에서 실행하기 쉽다.
- 응답시간, 처리량, 오류율 기준을 코드로 정의할 수 있다.

현재 저장소에는 k6 스크립트가 없으며 도입 시 `load-test/k6/` 구조를 별도로 제안한다.

## 4. 환경 원칙

- 운영과 분리된 부하 테스트 환경을 사용한다.
- 실제 고객 데이터와 운영 비밀정보를 사용하지 않는다.
- 운영과 비슷한 애플리케이션/DB 설정을 사용한다.
- 테스트 시간, 최대 부하, 중단 조건을 사전에 공유한다.
- CloudWatch 지표와 애플리케이션 로그를 동시에 수집한다.

## 5. 단계별 대상

### 1단계: 계좌 조회

현재 확인된 `GET /api/accounts`를 사용한다.

- 목적: HTTP, Spring Boot, JPA 조회 경로의 기준선 측정
- 위험: 데이터 변경 없음
- 초기 성공 기준 제안: p95 500ms 이하, 오류율 1% 미만

### 2단계: 로그인

- 정상 로그인과 실패 로그인 분리
- 비밀번호 해시 연산의 CPU 영향 측정
- 계정 잠금과 호출 제한 검증

### 3단계: 거래내역 조회

- 계좌별 데이터 크기에 따른 쿼리 시간 측정
- Pagination과 Index 효과 확인

### 4단계: 이체

- 가짜 계좌와 가짜 금액만 사용
- 잔액 보존과 중복 처리 여부 검증
- 동시 요청에서 Lost Update, Deadlock, Lock Wait 측정
- 멱등성 키로 동일 요청 중복 실행 방지 확인

## 6. 부하 유형

| 유형 | 목적 | 예시 |
| --- | --- | --- |
| Smoke | 스크립트와 환경의 기본 정상 여부 | VU 1~2, 1분 |
| Load | 예상 정상 부하 검증 | 예상 동시 사용자, 10~30분 |
| Stress | 한계와 실패 형태 확인 | 부하를 단계적으로 증가 |
| Spike | 갑작스러운 트래픽 증가 확인 | 짧은 시간에 VU 급증 |
| Soak | 메모리 누수·연결 누적 확인 | 중간 부하로 수 시간 |

## 7. 초기 시나리오 예시

실제 수치는 팀의 사용자 예측 후 확정한다.

```text
0~2분:   VU 0 → 10
2~7분:   VU 10 유지
7~12분:  VU 10 → 50
12~22분: VU 50 유지
22~25분: VU 50 → 0
```

## 8. 동시에 관찰할 지표

### k6

- 요청 수와 성공 수
- RPS
- p50, p95, p99
- 오류율
- API별 응답시간

### ALB/ECS

- TargetResponseTime
- HTTP 4xx/5xx
- ECS CPU와 메모리
- Task 수와 재시작

### JVM

- Heap 사용량
- GC 횟수와 정지 시간
- Thread 수
- DB Connection Pool 사용량

### RDS

- CPU
- DatabaseConnections
- Read/WriteLatency
- Slow Query
- Lock Wait와 Deadlock

## 9. 이체 정합성 검증

`정합성`은 동시에 많은 요청이 발생해도 데이터 규칙이 깨지지 않는 성질이다.

예를 들어 A 계좌에서 B 계좌로 1만원을 100번 이체했다면 다음을 검증한다.

- 성공한 이체 건수와 거래내역 건수가 일치한다.
- 전체 계좌 잔액의 합이 수수료 등을 제외하고 보존된다.
- 잔액이 허용되지 않은 음수가 되지 않는다.
- 같은 멱등성 키의 요청은 한 번만 반영된다.
- 실패한 거래는 출금과 입금이 모두 반영되지 않는다.

## 10. 중단 조건

- 오류율이 합의된 위험 기준을 초과한다.
- DB 또는 ECS가 위험한 자원 사용률에 도달한다.
- 데이터 정합성 오류가 발견된다.
- 모니터링이나 로그 수집이 동작하지 않는다.
- 다른 팀의 테스트나 서비스에 영향을 준다.

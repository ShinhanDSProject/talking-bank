# Talking Bank 보안 설계

> 상태: 최소 보안 기준 초안. 실제 금융정보를 처리한다면 조직 정책, 법률 및 보안 담당자 검토가 추가로 필요하다.

## 1. 보호 대상

- 사용자 개인정보: 이름, 이메일, 전화번호
- 인증정보: 비밀번호 해시, Access Token, Refresh Token
- 금융정보: 계좌번호, 잔액, 거래내역
- 시스템 비밀정보: DB 비밀번호, JWT 서명 키, 클라우드 자격 증명
- 운영정보: 로그, 배포 기록, 관리자 작업 기록

## 2. 기본 원칙

- 최소 권한: 업무에 필요한 권한만 부여한다.
- 다층 방어: 네트워크, 애플리케이션, 데이터 각 계층에서 보호한다.
- 비밀정보 분리: 코드와 설정 비밀값을 분리한다.
- 기본 차단: 필요한 연결만 명시적으로 허용한다.
- 추적 가능성: 인증, 배포, 변경 기록을 남긴다.

## 3. 인증과 권한

- 사용자 비밀번호는 BCrypt 같은 단방향 해시로 저장한다.
- 원문 비밀번호를 DB와 로그에 남기지 않는다.
- 관리자 AWS 계정에는 MFA를 적용한다.
- 사람은 장기 Access Key 사용을 피하고 SSO/Role을 우선한다.
- GitHub Actions는 가능하면 OIDC로 AWS Role을 임시 발급받는다.
- Access Token은 짧은 만료시간을 사용하고 Refresh Token 정책을 별도로 정의한다.

## 4. 비밀정보 관리

| 값 | 저장 위치 | 금지 위치 |
| --- | --- | --- |
| DB 비밀번호 | Secrets Manager 제안 | Git, Dockerfile, 로그 |
| JWT Secret | Secrets Manager 제안 | 프론트 환경 변수, Git |
| 로컬 가짜 비밀번호 | Git에서 제외한 `.env` | 커밋된 `.env` |
| AWS 권한 | IAM Role/OIDC | 소스 코드의 Access Key |

`VITE_` 접두사의 값은 브라우저 번들에 포함될 수 있으므로 비밀값을 넣지 않는다.

## 5. 데이터 보호

- 전송 중 암호화: 외부 통신은 TLS/HTTPS를 사용한다.
- 저장 시 암호화: RDS, S3, ECR, 로그의 암호화를 활성화한다.
- S3 Public Access Block을 활성화한다.
- RDS Public Access를 비활성화한다.
- 백업도 운영 데이터와 같은 수준으로 보호한다.
- 개발 환경에는 실제 고객 데이터를 사용하지 않는다.

## 6. 로그 마스킹

다음 값은 로그에 남기지 않는다.

- 비밀번호와 비밀번호 해시
- JWT 및 세션 쿠키
- DB 비밀번호
- 전체 계좌번호
- 주민등록번호 등 고유식별정보

계좌번호가 운영상 필요하면 최소 부분만 표시한다.

```text
원본: 110123456789
로그: 110-***-***789
```

## 7. 네트워크 보안

- CloudFront/ALB만 인터넷에 공개한다.
- ECS와 RDS는 Private Subnet에 배치한다.
- ALB→ECS, ECS→RDS 연결만 허용한다.
- 불필요한 관리 포트를 공개하지 않는다.
- 필요성과 위협 모델이 정리되면 AWS WAF를 적용한다.

## 8. 애플리케이션 보안

- 모든 입력에 길이, 형식, 범위 검증을 적용한다.
- 인증 실패와 권한 부족을 구분하되 민감한 내부 정보를 노출하지 않는다.
- CORS 허용 출처를 운영 도메인으로 제한한다.
- 인증 쿠키 사용 시 `Secure`, `HttpOnly`, 적절한 `SameSite`를 설정한다.
- 이체 API에는 인증, 권한 검사, 멱등성, 트랜잭션, 동시성 제어를 적용한다.
- Actuator는 필요한 endpoint만 공개한다.

## 9. 공급망과 배포 보안

- 의존성 버전을 lock 파일로 관리한다.
- Pull Request에서 테스트와 취약점 검사를 실행한다.
- 배포 Artifact와 Docker Image는 동일한 커밋에서 생성한다.
- 운영 배포 권한과 코드 병합 권한을 분리하는 것을 검토한다.
- 이미지 태그로 `latest`만 사용하지 말고 Git 커밋 SHA를 포함한다.

## 10. 보안 사고 시 초기 대응

1. 사고 범위와 영향을 확인한다.
2. 노출된 키나 토큰을 즉시 폐기·교체한다.
3. 관련 배포를 중단하고 증거 로그를 보존한다.
4. 영향받은 계정과 데이터 범위를 분석한다.
5. 복구 후 원인과 재발 방지책을 기록한다.

## 11. 검토 체크리스트

- [ ] Git 이력에 비밀정보가 없는가?
- [ ] 운영 DB가 Public Access로 설정되지 않았는가?
- [ ] IAM 정책에 불필요한 `*` 권한이 없는가?
- [ ] 로그에 토큰과 전체 계좌번호가 없는가?
- [ ] 운영 HTTPS가 강제되는가?
- [ ] 백업의 접근 권한과 암호화가 설정됐는가?

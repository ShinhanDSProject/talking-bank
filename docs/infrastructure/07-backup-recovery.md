# Talking Bank 백업 및 복구

> 상태: 정책 초안. RPO/RTO와 보존 기간은 비즈니스 책임자 승인이 필요하다.

## 1. 용어

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| Backup | 장애나 실수에 대비한 데이터 복사본 | RDS 자동 백업 |
| Restore | 백업에서 데이터를 되살리는 작업 | 새 RDS로 복원 |
| RPO | 허용 가능한 최대 데이터 손실 시간 | RPO 5분이면 최대 5분 데이터 손실 허용 |
| RTO | 장애 후 복구까지 허용 가능한 시간 | RTO 1시간이면 1시간 안에 복구 목표 |
| PITR | 특정 시점으로 DB를 복원하는 기능 | 삭제 직전 시점으로 복원 |

## 2. 보호 대상

| 대상 | 백업 방식 제안 | 중요도 |
| --- | --- | --- |
| RDS MariaDB | 자동 백업, PITR, 수동 Snapshot | 매우 높음 |
| S3 Web Artifact | Git/CI 재생성, 필요 시 Versioning | 중간 |
| ECR Image | 커밋 SHA 태그와 보존 정책 | 높음 |
| 인프라 설정 | Terraform과 Git 이력 | 매우 높음 |
| Secrets | Secrets Manager 버전과 별도 비상 절차 | 매우 높음 |
| 로그 | CloudWatch 보존 정책 | 감사 요구에 따라 결정 |

## 3. 초기 정책 제안

- 개발 DB: 비용을 고려한 짧은 자동 백업 보존 기간
- 운영 DB: 자동 백업과 PITR 활성화
- 운영 배포 전 중요한 DB 변경이 있으면 수동 Snapshot 생성 검토
- 백업 암호화 활성화
- 백업 접근 권한 최소화
- 운영 DB 삭제 방지 설정 적용

정확한 보존 일수와 RPO/RTO는 아직 미정이다.

## 4. 장애 시나리오

### 애플리케이션 배포 오류

- 데이터 손상이 없으면 직전 ECS 버전으로 롤백한다.

### 실수로 데이터 삭제

- 삭제 시각을 확인한다.
- 삭제 직전 시점으로 새 RDS를 복원한다.
- 원본과 복원 DB를 비교한다.
- 승인된 절차로 서비스 연결 또는 필요한 데이터만 복구한다.

### RDS 장애

- Multi-AZ Failover 상태를 확인한다.
- 자동 복구 실패 시 Snapshot/PITR로 새 인스턴스를 만든다.
- 보안 그룹, Secret, DNS/접속 정보를 갱신한다.

### 리전 단위 장애

- 현재 단계에서는 비용과 요구사항을 확인해 별도 DR 리전을 결정한다.
- 결정 전에는 단일 리전 장애가 남은 위험임을 명시한다.

## 5. RDS 복구 절차 초안

1. 장애 및 데이터 손상 시각을 확정한다.
2. 복원 목표 시점을 정하고 변경 승인을 받는다.
3. 기존 DB를 덮어쓰지 않고 새 RDS로 복원한다.
4. Private DB Subnet과 전용 보안 그룹을 적용한다.
5. Schema와 핵심 데이터 건수를 확인한다.
6. 애플리케이션 연결 테스트를 수행한다.
7. 점검 시간 동안 쓰기 요청 처리 정책을 적용한다.
8. Secret의 DB endpoint를 안전하게 변경한다.
9. ECS를 재배포하고 Smoke Test한다.
10. 기존 DB는 조사와 되돌리기를 위해 즉시 삭제하지 않는다.

## 6. 복구 테스트

백업이 존재하는 것만으로는 충분하지 않다. 실제로 복원할 수 있어야 한다.

- 정기적으로 비운영 환경에 복원한다.
- 복원 시작·완료 시간을 기록한다.
- 애플리케이션 연결과 핵심 쿼리를 검증한다.
- 측정한 복구 시간이 RTO를 만족하는지 확인한다.
- 실패 원인과 절차 개선사항을 기록한다.

## 7. 삭제 보호

- 운영 RDS Deletion Protection 활성화
- Terraform 삭제 시 보호 설정 검토
- 운영 Snapshot 삭제 권한 제한
- S3 중요 Bucket의 Versioning과 삭제 정책 검토
- 운영 자원 삭제는 별도 승인 절차 적용

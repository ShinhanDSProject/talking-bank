# Phase 1 — 은행 코어

계좌가 "은행 계좌"로 성립하는 최소 구성이다 — 누구 것인지, 얼마 있는지, 옮길 수 있는지, 무슨 일이 있었는지. 모든 확장 도메인이 이 위에 올라간다.

- 진입 조건: 없음. 프로젝트의 시작이다.
- 공통 규칙: [04-domain.md](../04-domain.md) — 금액·송금·동시성·멱등성 규칙과 코어가 열어둘 자리. 이 문서보다 우선한다.

## 범위

### P0 — Phase 1의 필수

| ---- | ----------------- | ---------------------------------------------------------- |
| AUTH | 회원가입 · 로그인 | 이메일/비밀번호 가입, JWT 로그인, 토큰 재발급, 로그아웃    |
| ACCT | 계좌 조회         | 내 계좌 목록, 계좌별 잔액, 계좌 상세                       |

| TXN  | 거래내역          | 계좌별 입출금 내역, 최신순, 기간 필터, 상세                |

- **FDS·관리자 화면** — [Phase 2](02-risk.md). 코어는 이체에 "출금 평가 훅"만 열어둔다. [04-domain.md](../04-domain.md#이후-phase를-위해-코어가-열어둘-자리) 참고.

## 기능 명세

각 기능의 **수용 조건(AC)** 을 적는다. 상세 API 설계는 구현 담당자가 이슈에서 한다.

### AUTH — 회원가입 · 로그인

- 이메일·비밀번호·휴대폰 번호로 가입한다. 이메일·휴대폰 중복을 확인한다.
- 로그인 성공 시 Access Token + Refresh Token을 발급한다. 정책은 [06-conventions.md](../06-conventions.md#인증-정책) 참고.
- 인증이 필요한 API는 토큰 없이 호출하면 401을 돌려준다.
- 로그아웃하면 Refresh Token이 무효화된다.
- `role`(`USER` / `ADMIN`)은 지금 만든다. Phase 2 관리자 화면이 쓴다.

**AC**

- [ ] 중복 이메일로 가입 시 명확한 에러 코드가 온다.
- [ ] 만료된 Access Token으로 호출 시 401, Refresh로 재발급이 된다.
- [ ] 로그아웃 후 Refresh Token으로 재발급이 안 된다.

### ACCT — 계좌 조회

- 가입 시 기본 입출금 계좌가 하나 자동 개설된다.
- 내 계좌 목록과 각 잔액을 본다. 다른 사람의 계좌는 볼 수 없다.

**AC**

- [ ] 다른 사용자의 계좌 ID로 조회하면 403 또는 404가 온다.
- [ ] 잔액은 거래내역의 합과 항상 일치한다. (테스트로 검증)

### XFER — 송금

처리 순서와 동시성·멱등성 규칙은 [04-domain.md 송금 규칙](../04-domain.md#송금-규칙)을 따른다. Phase 5~7의 카드 출금·예수금 이체·보험료 납입이 전부 이 로직을 재사용한다.

- 출금 계좌(내 계좌) · 입금 계좌번호 · 금액 · 메모를 입력한다.
- 확인 화면에서 수취인 이름을 보여준 뒤 실행한다.
- 실행 결과(성공 / 잔액 부족 / 계좌 상태 오류)를 화면에 보여준다. FDS 보류·차단 결과는 Phase 2에서 추가된다.
- 출금 전에 **출금 평가 훅**을 호출한다. Phase 1의 구현체는 항상 통과시킨다.

**AC**

- [ ] 잔액보다 큰 금액은 거절되고 잔액이 변하지 않는다.
- [ ] 출금 계좌와 입금 계좌가 같으면 거절된다.
- [ ] 동일 계좌에 동시 출금 N건을 보내도 최종 잔액이 음수가 되지 않는다. (동시성 테스트)
- [ ] 입금 처리 중 예외가 나면 출금도 롤백된다. (트랜잭션 테스트)
- [ ] 같은 요청을 두 번 보내도(더블 클릭) 한 번만 이체된다. (멱등성)

### TXN — 거래내역

- 계좌별 입금/출금 내역을 최신순으로 본다. 기간 필터를 지원한다.
- 각 거래에는 거래번호, 유형(입금/출금), 금액, 거래 후 잔액, 상대 계좌, 시각, 메모가 있다.

**AC**

- [ ] 송금 1건이 출금 계좌 내역과 입금 계좌 내역 양쪽에 각각 1건씩 남는다.
- [ ] 목록은 페이지네이션된다. (기본 20건)

## 도메인 모델

엔티티 이름과 상태값은 여기 적힌 것을 쓴다.

```
User 1 ──── N Account 1 ──── N Transaction
                │                   ▲
                │                   │ 이체 1건 = 출금 거래 1 + 입금 거래 1
                │                   │
                └──── N Transfer ───┘
```

### User

| 필드      | 타입     | 비고                      |
| --------- | -------- | ------------------------- |
| id        | Long     |                           |
| email     | String   | unique, 로그인 ID         |
| password  | String   | BCrypt 해시               |
| name      | String   | 수취인 확인 화면에 보여줌 |
| phone     | String   | unique                    |
| role      | enum     | `USER`, `ADMIN`           |
| createdAt | DateTime |                           |

세부 컬럼(생년월일, 약관 동의 등)은 [02-scope.md 설계 전 결정 사항](../02-scope.md#설계-전-결정-사항)에 따른다.

### Account

| 필드          | 타입           | 비고                                                |
| ------------- | -------------- | --------------------------------------------------- |
| id            | Long           |                                                     |
| accountNumber | String         | unique. 형식은 `110-123-456789` 같은 하이픈 포함    |
| user          | User           |                                                     |
| accountType   | enum           | 지금은 `CHECKING` 하나. Phase 3·6에서 값이 늘어난다 |
| productName   | String         | "주거래 입출금통장" 등. 상품 마스터는 Phase 3에서   |
| balance       | **BigDecimal** | precision 19, scale 2. 음수 불가                    |
| currency      | String         | 항상 `KRW`. 컬럼만 유지                             |
| status        | enum           | `ACTIVE`, `DORMANT`, `CLOSED`                       |
| openedAt      | Date           |                                                     |

이미 `apps/api`에 구현되어 있다. `user` 연관과 `accountType`을 추가하면 된다.

계좌 상태:

| 상태      | 조회 | 출금 | 입금 | 비고                    |
| --------- | ---- | ---- | ---- | ----------------------- |
| `ACTIVE`  | O    | O    | O    | 정상                    |
| `DORMANT` | O    | X    | O    | 휴면. 시연용으로만 존재 |
| `CLOSED`  | O    | X    | X    | 해지. 시연용으로만 존재 |

상태를 바꾸는 기능은 향후 후보다. 지금은 시드 데이터로만 만든다.

### Transaction (거래)

| 필드                      | 타입       | 비고                                                    |
| ------------------------- | ---------- | ------------------------------------------------------- |
| id                        | Long       |                                                         |
| account                   | Account    | 이 거래로 잔액이 바뀐 계좌                              |
| type                      | enum       | `DEPOSIT`(입금), `WITHDRAWAL`(출금)                     |
| sourceType                | enum       | 지금은 `TRANSFER` 하나. Phase 3·5·6·7에서 값이 늘어난다 |
| amount                    | BigDecimal | 항상 양수. 방향은 `type`이 정한다                       |
| balanceAfter              | BigDecimal | 거래 직후 잔액. 내역 화면에 보여주고 정합성 검증에 씀   |
| counterpartyAccountNumber | String     | 상대 계좌번호                                           |
| transfer                  | Transfer   | 어느 이체에서 생긴 거래인지                             |
| memo                      | String     |                                                         |
| createdAt                 | DateTime   |                                                         |

**불변이다.** UPDATE·DELETE 하지 않는다.

### Transfer (이체)

| 필드           | 타입       | 비고                                            |
| -------------- | ---------- | ----------------------------------------------- |
| id             | Long       |                                                 |
| idempotencyKey | String     | unique. 클라이언트가 생성(UUID). 중복 요청 방지 |
| fromAccount    | Account    |                                                 |
| toAccount      | Account    |                                                 |
| amount         | BigDecimal |                                                 |
| memo           | String     |                                                 |
| status         | enum       | 아래 상태 참고                                  |
| failureReason  | String     | 실패·차단 사유                                  |
| requestedAt    | DateTime   |                                                 |
| completedAt    | DateTime   |                                                 |

상태 전이:

```
REQUESTED ──▶ COMPLETED          정상 완료
    │
    ├──────▶ PENDING_AUTH ──▶ COMPLETED   FDS 보류 → 추가 인증 통과   (Phase 2)
    │              └────────▶ FAILED      추가 인증 실패 또는 만료     (Phase 2)
    ├──────▶ BLOCKED                      FDS 차단                     (Phase 2)
    └──────▶ FAILED                       잔액 부족, 계좌 상태 이상 등
```

`COMPLETED`, `BLOCKED`, `FAILED`는 종료 상태다. 다시 바뀌지 않는다. `PENDING_AUTH`·`BLOCKED`는 Phase 2에서 쓰이지만 enum 값은 지금 정의한다.

## 시드 데이터

로컬 개발과 시연을 위해 `local` 프로필에서 자동 생성한다. 데이터가 하나도 없을 때만 넣는다(`AccountSeeder` 방식).

- 일반 회원 3명 (각 계좌 1~2개), 관리자 1명 (`role`은 지금 있다. 화면은 Phase 2)
- 계좌 잔액은 시연 시나리오가 돌아갈 만큼 (예: 1,000,000원)

## 진행

### Step 1-1 — 기반 구축

목표: **로그인해서 내 계좌 목록이 보인다.** 배포된 주소에서.

| 영역   | 할 일                                                                                              |
| ------ | -------------------------------------------------------------------------------------------------- |
| 공통   | 컨벤션·인증 정책·응답 포맷 확정. [설계 전 결정 사항 5개](../02-scope.md#설계-전-결정-사항) 답 받기 |
| 공통   | Spring Boot 3.5.x 전환 머지 (PR #28)                                                               |
| 백엔드 | User 엔티티(`role` 포함), 회원가입·로그인·토큰 재발급 API, Security 설정                           |
| 백엔드 | Account에 User 연관·`accountType` 추가, 내 계좌 목록 API를 인증 기반으로                           |
| 프론트 | 폴더 구조 확정, 디자인 시스템 기본(색·타이포·버튼·입력), 로그인·가입 화면                          |
| 프론트 | 로그인 후 계좌 목록 화면 (이미 있는 화면에 인증 연결)                                              |
| 인프라 | docker-compose에 Redis 추가(확정 시), 서버 1대에 배포 스크립트                                     |

**완료 조건**: 팀원 전원이 배포 주소에서 가입 → 로그인 → 계좌 목록을 본다.

### Step 1-2 — 송금과 거래내역

목표: **송금이 동시성까지 정확히 동작한다.**

| 영역   | 할 일                                                                                             |
| ------ | ------------------------------------------------------------------------------------------------- |
| 백엔드 | Transfer·Transaction 엔티티(`sourceType` 포함), 송금 API (트랜잭션·비관적 락·멱등성·출금 평가 훅) |
| 백엔드 | 동시성 테스트, 롤백 테스트 — [XFER AC](#xfer--송금) 전부                                          |
| 백엔드 | 거래내역 조회 API (페이지네이션, 기간 필터)                                                       |
| 백엔드 | 공통 에러 응답·예외 처리, Swagger                                                                 |
| 프론트 | 송금 화면 (입력 → 수취인 확인 → 실행 → 결과), 거래내역 화면                                       |
| 프론트 | API 에러 코드에 따른 메시지 표시 공통화                                                           |

**완료 조건**: 두 계정으로 로그인해 서로 송금하고, 양쪽 거래내역에 남는 것을 본다. 동시성·롤백·멱등성 테스트가 통과한다.

### Step 1-3 — 안정화

목표: **끊기지 않는 시연, 설명할 수 있는 코드.**

- 시연 시나리오 반복 실행, 발견되는 버그 수정. **새 기능 추가 금지**
- 예외 케이스 정리 — 잔액 부족, 만료 토큰, 존재하지 않는 계좌, 네트워크 오류
- README·docs 최신화
- 회고 — 잘 된 것, 안 된 것, 다시 한다면

**완료 조건**: [기능 명세](#기능-명세)의 AC 전부 체크. [시연 시나리오](../05-schedule.md#시연-시나리오) Phase 1이 끊기지 않고 돈다.
